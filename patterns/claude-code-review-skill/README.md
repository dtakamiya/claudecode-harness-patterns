# Claude Code Review Skill

## 概要

工程やゲートに束縛されず、任意のリポジトリで単独動作する汎用コードレビュースキルの設計パターンです。既存の[Development Harness](../claude-code-development-harness/README.md)がPHASE-9として持つレビューエージェント群とは**適用レイヤが異なり、併存します**。

中核となる主張は1つです。**レビュー品質は指摘の量ではなく、指摘を出さない能力（precision）で決まる**。この設計はそれを構造で担保します。

## 向いているケース

- 単発のPRレビュー、コミット前の自己チェック
- 工程管理のないリポジトリ、他プロジェクトへの持ち込み
- レビュー結果を人間の判断材料として使いたい（自動修正は望まない）
- 偽陽性がレビュー体験を壊している

## 向いていないケース

- 工程のゲート条件を判定したい（[Development Harness](../claude-code-development-harness/README.md)のPHASE-9エージェントを使う）
- 網羅的な脆弱性監査（本スキルはprecision優先のため見逃しを許容する）
- レビューと同時に修正まで行いたい（本スキルは設計上コードを変更しない）
- 本番障害対応（[Incident Response Harness](../claude-code-incident-response-harness/README.md)へ）

## 設計の要点

### 1. 反証ゲート（キル・ゲート）

探索と反証を**別ステップに分ける**。候補を広く出したあと、各候補に対し「実際に失敗する具体的な入力・状態を書けるか」を問い、**書けない候補は破棄する**。

根拠は[Refute-or-Promote](https://arxiv.org/abs/2604.19049)の実測です。同論文は、**10のレビュアーが全員一致で「存在しないBleichenbacher padding oracle」を承認し、それを潰したのは合議ではなく1件の実証テストだった**と報告しています。レビューを重ねても偽陽性は落ちず、実証ゲートのみがそれを排除しました。同手法は171候補の約79%を公開前に排除しています。

### 2. `failure_scenario` を報告の必須要素にする

指摘1件ごとに「具体的な入力・状態 → 誤った出力・クラッシュ」を書かせます。書けないものは報告に載せられないため、反証ゲートが報告形式でも強制されます。

### 3. `disallowed-tools` でEdit/Writeを外す

レビュアーは修正しません。本文に「修正するな」と書いても推論で回避され得ますが、`disallowed-tools`はツールプールから除去するため回避できません。[Steering Claude Code](https://claude.com/blog/steering-claude-code-skills-hooks-rules-subagents-and-more)が述べる「禁止は本文でなく機構で強制する」の適用です。

レビューと修正を同一ターンで行うと、レビュアーが自分の修正を再レビューすることになり独立性が失われます。

### 4. 対象確定は低自由度、欠陥探索は高自由度

公式の「degrees of freedom を対象の脆さに合わせる」原則の適用です。

| 層 | 自由度 | 理由 |
|---|---|---|
| 対象確定 | 低（コマンド厳密指定） | 対象がずれると以降すべてが無効になる「細い橋」 |
| 欠陥探索 | 高（観点リストのみ） | 有効な経路が多数ある「開けた野原」 |
| 報告 | 中（テンプレート＋逸脱許容） | 構造は要るが状況適応も要る |

対象を取得できない場合は**そこで停止**し、推測でリポジトリ全体を読み始めません。

### 5. Progressive Disclosure

SKILL.md本体を**150行以内**に抑え、観点の詳細を`reference/`へ退避します。公式の上限は500行ですが、既存のレビューエージェント（719行）がこれを大きく超えている反省を踏まえた設定です。

参照は**1階層まで**。公式は、ネストした参照ではClaudeが`head -100`で部分読みし情報が欠落すると明記しています。

### 6. precision優先を明示的に選ぶ

[Deep Code Review](https://www.augmentcode.com/guides/deep-code-review-recall-vs-precision)によれば、recall優先が機能するには3条件（全体インデックス・理由付け・人間の承認ゲート）が要ります。本スキルは単独動作を前提とするため全体インデックスを持てず、**precision優先を採ります**。

20万件超のPRを対象に17のAIレビューツールを評価した[ベンチマーク](https://www.codeant.ai/blogs/ai-code-review-benchmark-results-from-200-000-real-pull-requests)では、上位でも**F1約52%**（precision 52.2% / recall 51.1%）にとどまります。指摘の約半分が外れる水準であり、precision と recall のどちらを取るかは設計判断であって、暗黙に決めてよいものではありません。

代償も明示します。本スキルは**「見逃さないレビュー」ではなく「出した指摘が信頼できるレビュー」**です。

ただし当初の設計から一点緩和しました。recall優先の3条件のうち欠けるのは「リポジトリ全体のセマンティックインデックス」だけであり、取りこぼす欠陥の多くは**差分に現れた識別子から参照を1ホップ辿れば確証できる**ものでした。そこで Step 3 に差分起点の探索を追加しています（[設計書 §2.4.1](docs/design.md)）。起点を差分中の識別子に限定するため全体走査には退行せず、辿った結果は反証の材料になるため precision も犠牲にしません。

それでも1ホップで辿れない欠陥（設計レベルの誤り、複数サービスをまたぐ契約違反）は取りこぼします。**「差分から辿れる範囲では見逃さない」**までです。

## 既存パターンとの関係

| パターン | 関係 |
|---|---|
| [Cookbook Harness](../claude-code-cookbook-harness/README.md) | P2（トリガーフレーズ列挙）とP3（権限拘束ロール）を継承。P4（敵対的ロール議論）とは発想を共有するが、本スキルは単一コンテキスト内で自己反証する点が異なる |
| [Development Harness](../claude-code-development-harness/README.md) | 別レイヤ。工程束縛型のレビューは引き続き既存エージェントが担う |
| [Human Gate Policy](../human-gate-policy.md) | 本スキルは判断材料を提供するのみで、承認判断は同ポリシーに従う |
| [Change Intent Record](../change-intent-record.md) | 判断根拠を残す発想を共有 |

## 未解決事項

設計書 §8 に記載の通り、**evalの実行基盤は含みません**。Agent Skillsのevalを実行する組み込みの仕組みは現時点で存在せず、`tasks.jsonl`は仕様にとどまります。またprecisionの数値目標は、ベースライン測定前に置くと数値合わせが起きるため設定していません。
