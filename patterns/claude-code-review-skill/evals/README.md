# レビュースキル Eval

[設計書 §6](../docs/design.md) で定めた評価タスクの定義です。

## ファイル

- `tasks.jsonl` — 評価タスク6件。1行1タスクのJSON Lines形式。

## 前提

**実行基盤は含みません。** 公式ドキュメントが明記する通り、Agent Skillsのevalを実行する組み込みの仕組みは現時点で存在せず、利用者が独自の評価システムを構築する必要があります。`tasks.jsonl` は仕様であり、実行スクリプトは別途要ります。

## 設計方針

[Demystifying evals for AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents) に従います。

- **良いタスク**とは「2人のドメイン専門家が独立に同じ pass/fail へ到達するもの」
- **経路ではなく成果物を採点する** — 手順の遵守ではなく報告内容を評価する
- **正例と負例の両方**を置く — 負例（E2, E3）が precision の実測に不可欠
- **各タスクを複数回試行する** — 1回の結果で判断しない
- **pass rate 0% はタスクの故障を疑う** — 能力不足ではなくタスクが壊れているサインであることが多い

## タスク一覧

| ID | 種別 | 測定対象 | グレーダー | 狙い |
|---|---|---|---|---|
| E1 | 正例 | 検出率 | コードベース | 境界条件の欠陥を検出できるか |
| E2 | 負例 | **precision** | コードベース | 欠陥がないとき指摘を出さずにいられるか |
| E3 | 負例 | precision | モデルベース | 仕様通りの挙動を欠陥と誤認しないか |
| E4 | ガードレール | 対象規律 | コードベース | 対象を取得できないとき停止できるか |
| E5 | 正例 | 検出率 | コードベース | 複数ファイルにまたがる不整合を検出できるか |
| E6 | 負例 | **反証ゲート** | モデルベース | 到達不能な候補を棄却し、棄却理由を述べられるか |
| E7 | 負例 | 対象規律 | モデルベース | 探索が全体走査へ退行していないか |

E2 が最重要です。2026年のベンチマークが示す通り、precision は「指摘を出さない能力」で決まります。

**E5 は差分起点の探索が働くかを測ります。** [設計書 §2.4.1](../docs/design.md) の改訂により、差分に現れた識別子から参照を1ホップ辿る指示が Step 3 に加わりました。両ファイルが差分に含まれる場合は検出できるべきです。ただし1ホップで辿れない欠陥（設計レベルの誤り、複数サービスをまたぐ契約違反）は依然として構造的に取りこぼします。

**E7 は E5 の裏側です。** 探索を足したことで「全体走査への退行」というリスクが生じました。差分と無関係なファイルを読み漁っていないかを測ります。E5 と E7 は**同時に通らなければ意味がありません**。片方だけなら、探索しないか、探索しすぎているかのどちらかです。

**E6 は Step 4（反証ゲート）を直接測る唯一のタスクです。** E1〜E5 は「結果として正しい報告が出たか」しか見ないため、反証を省略して偶然正解した場合と区別できません。E6 は明示的な棄却と棄却理由を要求することで、ゲートの実行そのものを判定します。

## グレーダーの選択

コードベースを優先し、機械判定できない部分だけモデルベースへ回します。公式はコードベースグレーダーを「高速・安価・客観的・再現可能・デバッグ容易」と評価しています。

## 記録する指標

| 指標 | 算出 | 位置づけ |
|---|---|---|
| precision | 真の指摘 / 全指摘 | **主目標** |
| 偽陽性率 | E2, E3 での誤指摘率 | 0に近づける |
| 検出率 | E1, E5 での既知欠陥の検出割合 | 副目標（E5は探索機構の実効性を兼ねる） |
| 探索規律 | E7 で差分外の無関係なファイルを読んでいないか | 全試行で遵守 |
| 手順遵守 | 反証記述（Step 4）の有無 | 全試行で存在すべき |

precision を主目標に置く根拠は[設計書 §2.4](../docs/design.md)にあります。リポジトリ全体のインデックスを持たない構成で recall を追うと、偽陽性がそのまま利用者へ届くためです。

## モデル横断テスト

公式は「使う予定のすべてのモデルでテストせよ」と述べます。特に **Haiku で Step 4（反証ゲート）が省略されないか**を重点的に確認してください。手順の省略は precision の直接の劣化につながります。

## 拡張

初期セット6件は出発点です。公式は「実際の失敗から取った20〜50タスクが良い出発点」としています。実使用で偽陽性が出るたびに、そのパターンを負例タスクとして追加してください（Ratchetパターン）。
