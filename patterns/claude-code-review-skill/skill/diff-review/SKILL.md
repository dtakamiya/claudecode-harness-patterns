# Diff Review

差分に限定したコードレビューを行う。**precision優先**であり、見逃しよりも誤指摘を避ける。

このスキルはコードを修正しない。修正が必要なら報告後に別の能力へ渡す。

## 進行チェックリスト

以下を応答へコピーし、完了ごとに埋めながら進める。

```text
Review Progress:
- [ ] Step 1: 対象を確定し、行数と範囲を宣言する
- [ ] Step 2: 変更意図を推定する
- [ ] Step 3: 観点別に候補を洗い出す
- [ ] Step 4: 各候補を反証する（キル・ゲート）
- [ ] Step 5: 生存した指摘のみ深刻度を付けて報告する
```

## Step 1: 対象確定

`collect_diff.sh` を実行する。引数はユーザーの指定をそのまま渡す。

**パスは必ず `${CLAUDE_SKILL_DIR}` を前置する。** 相対パスだとカレントディレクトリ次第で「ファイルが無い」となり、その失敗は exit 0 で返るため、対象なしのままレビューが進む。

```bash
S="${CLAUDE_SKILL_DIR}/scripts/collect_diff.sh"
bash "$S"              # 作業ツリーの未コミット変更
bash "$S" <branch>     # merge-base 起点の差分
bash "$S" '#123'       # PR の差分（gh 必須）
bash "$S" -- <path>    # 当該パスに触れている差分のみ
```

読み始める前に**レビュー範囲を宣言する**。「対象: N ファイル / M 行、範囲: <説明>」。

**取得に失敗した場合、対象が0行の場合、スクリプトを実行できない場合は、そこで停止する。** 失敗を報告し、推測でリポジトリ全体を読み始めない。対象がずれたレビューは、指摘が正しくても無効である。

**すべての引数形式で対象は差分に限定する。** パス指定を「配下の全体」と解釈してはならない。全体監査は対象外である。この規律は Step 3 の探索にも適用される。

リンタ・型検査器が設定済みなら先に実行し、出力と重複する指摘は出さない（無くても構わない）。

## Step 2: 変更意図の推定

欠陥を探す前に、「この変更は何を達成しようとしているか」を1〜2文で言語化する。

判断材料はdiff本体、コミットメッセージ、PR説明、コメント、テスト、そしてこの会話の直前の文脈である。

**意図が読み取れない場合は「意図不明」として報告に含める。推測で埋めない。** 意図を取り違えたまま探索すると、仕様通りの挙動を欠陥として報告する典型的な偽陽性が生まれる。

## Step 3: 候補の洗い出し（広く出す）

観点別に候補を出す。この段階では偽陽性を許容してよい。判断はStep 4で行う。

| 観点 | 参照 |
|---|---|
| 正当性・境界・並行性 | [reference/correctness.md](reference/correctness.md) |
| セキュリティ | [reference/security.md](reference/security.md) |
| 保守性 | [reference/maintainability.md](reference/maintainability.md) |

参照ファイルは**該当する観点に触れたときだけ読む**。全部を先読みしない。候補を出したら、Step 4 の前に [reference/gotchas.md](reference/gotchas.md)（実測された偽陽性パターン）と一度照合する。

### 差分の外側を読む

シグネチャ変更、公開APIの変更、新規エンドポイントの追加、定数の変更が差分にあれば、**その識別子を起点に参照箇所を Grep で引く**。差分だけでは判定できない欠陥（認可漏れ、呼び出し規約の不整合）はこれでしか取れない。

手順は [reference/tracing.md](reference/tracing.md)。**全体走査ではない**点に注意する。起点は必ず差分中の識別子であり、パス配下を舐めることは Step 1 の規律に反する。

読めなかった場合は「確証なし」と報告に書き、blocking にしない。

## Step 4: 反証（キル・ゲート）

**このステップは省略しない。** ここがこのスキルの中核である。

Step 3で出した候補それぞれに対し、以下を明示的に試みる。

1. この指摘が誤りであるとしたら、その理由は何か
2. 実際に失敗する具体的な入力・状態を書けるか
3. 書けないなら、なぜ書けないのか

**2が書けない候補は破棄する。** 「もっともらしさ」では偽陽性は落ちない。具体的な失敗シナリオを書けるかどうかだけが判別に使える。

**書けるなら、可能な範囲で実際に確かめる。** 実測は推論より強い。既存テストの実行、型検査・リンタ、境界値の手計算（算術は必ず検算する）。実行できたら、その結果を根拠として報告に書く。

**副作用のある実行はしない**（ネットワーク送信、ファイル書き換え、マイグレーション、外部サービス呼び出し）。手段がなければ推論で構わない。

典型的な棄却理由: 直前のガード節で当該値が排除されている / 呼び出し元が単一スレッドに限定されている / コメントとテストが挙動を意図として明示している / 到達経路が存在しない。

棄却した候補は報告の「検討して棄却した候補」節へ、**棄却理由とともに**記す。沈黙して消さない。

## Step 5: 報告

生存した指摘のみを出す。1件あたりの必須要素は4つ。

| 要素 | 内容 |
|---|---|
| `file:line` | クリック可能な位置 |
| `severity` | `blocking` / `non-blocking` の2値のみ |
| `summary` | 欠陥の一文記述 |
| `failure_scenario` | **具体的な入力・状態 → 誤った出力・クラッシュ** |

`failure_scenario` を書けない指摘は報告に載せない。判定基準は [reference/severity.md](reference/severity.md)。報告全体の必須節は「**検討して棄却した候補**」である。Step 4 の実行証跡はここにしか現れないため省略できない。

### 出力形式

```markdown
## レビュー結果

**対象**: <範囲、N ファイル / M 行>
**変更意図**: <1〜2文。読み取れなければ「意図不明」>

### 指摘

#### 1. [blocking] <summary>
- **位置**: `path/to/file.ts:42`
- **失敗シナリオ**: <入力・状態> → <誤った出力・クラッシュ>

### 検討して棄却した候補（指摘ゼロでも必須）

- <候補>: <棄却理由（どのガード節・どの制約により到達しないか）>
- 候補が出なかった場合: <見た観点と、何も出なかった旨>

### 判定

blocking N 件 / non-blocking M 件
```

**指摘がゼロなら、ゼロと明示的に報告する。** 何か書かなければならないという圧力が、偽陽性の主要な発生源である。「blocking 指摘はありません」と述べて終えてよい。

ただし「**検討して棄却した候補**」節は、指摘の有無にかかわらず**常に書く**。Step 3 で候補が1件も出なかった場合は、その旨と**どの観点を見て何も出なかったのか**を記す。この節が空のまま終わる報告は、Step 4 を実行した報告と省略した報告を区別できないため、認められない。

このスキルは「見逃さないレビュー」ではなく「出した指摘が信頼できるレビュー」である。複数ファイルにまたがる欠陥や、リポジトリ全体の文脈を要する欠陥は構造的に取りこぼす。網羅性が要るなら、その旨を報告に添える。

レビューを会話の文脈から切り離して独立に走らせたい場合は、`Agent` ツールで `Explore` エージェントへ渡すよう案内する。ただし独立実行では直前の実装意図（Step 2 の判断材料）が失われるため、既定にはしない。
