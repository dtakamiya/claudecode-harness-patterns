# 深刻度の判定基準

深刻度は **2値のみ**とする。3段階以上にすると境界の議論が発生し、利用者の判断コストが上がる。

## 判定の単一の問い

> **この指摘を理由に、マージを止めるべきか。**

止めるべきなら `blocking`、それ以外はすべて `non-blocking`。

## blocking

以下のいずれかに該当し、かつ `failure_scenario` を具体的に書けるもの。

- 正しい入力に対して**誤った結果**を返す
- クラッシュ、ハング、無限ループ、リソース枯渇を起こす
- **データを破壊する / 失う**（誤った更新、削除、ロールバックされない部分適用）
- 差分が**新たに導入した**セキュリティ欠陥で、攻撃者の到達経路を示せるもの
- 秘密情報の混入・漏洩
- 公開インターフェースを壊し、呼び出し側が差分に含まれていない

## non-blocking

上記に当てはまらないすべて。以下を含む。

- 保守性の指摘 — ほぼ常にこちら
- テストの不足
- 差分外の既存コードに元からある問題（「差分外」と明記する）
- 到達経路を確証できないセキュリティ上の懸念（特に認可。2つ目のファイルを読まないと確証できないことが多い）
- エッジケースではあるが、実運用で到達するとは言えないもの

## 迷ったときの規則

**`failure_scenario` を書き切れない指摘は、`non-blocking` ですらなく報告しない。** これは深刻度の問題ではなく、SKILL.md Step 4のゲートを通過していないということである。

`blocking` にすべきか迷ったなら `non-blocking` にする。誤って blocking と判定すると、利用者はマージを止めて調査に時間を使い、空振りだったと分かる。これが以降の指摘への信頼を落とす。逆方向の誤り（本来 blocking を non-blocking にする）は、指摘自体は利用者へ届いているため回復可能である。
