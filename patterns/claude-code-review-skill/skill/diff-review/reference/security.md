# セキュリティ

**このスキルは網羅的な脆弱性監査ではない。** 差分に現れた変更が新たに導入する脆弱性のみを対象とする。既存コードの監査は対象外である。

セキュリティ指摘は偽陽性の代償が特に大きい（利用者の時間を奪い、以降の指摘への信頼を落とす）。SKILL.md Step 4の反証を通し、**攻撃者が実際に到達できる経路を書けないものは破棄する**。

## 入力検証と注入

- SQL: 文字列連結でクエリを組み立てていないか。プレースホルダを使っているか
- コマンド実行: シェル経由の実行にユーザー入力が渡っていないか
- パス操作: `../` によるディレクトリトラバーサル。結合後のパスが想定ディレクトリ配下か検証しているか
- テンプレート / HTML: エスケープなしでユーザー入力を埋め込んでいないか（XSS）
- デシリアライズ: 信頼できない入力を型情報付きで復元していないか

反証の観点: その入力は本当に外部から到達するか。内部の定数・列挙値・型で既に制約されていないか。

## 認証・認可

- 新規に追加されたエンドポイント・ハンドラに認証チェックがあるか
- **オブジェクトレベルの認可**: 認証済みユーザーが、他人のリソースIDを指定して到達できないか（IDOR）
- 権限判定をクライアント側の値（リクエストボディのrole等）に依存していないか

**確認手順**: 認可の欠陥は「呼び出し側のミドルウェア定義」など2つ目のファイルを読まないと判定できないことが多い。新規・変更されたエンドポイントについては、SKILL.md Step 3 の探索でルーティング定義と**同種の既存ハンドラ1件**を読み、適用方法を比較する（手順は tracing の参照ファイル）。既存の全ハンドラが認可を通しているのに新規の1件だけ通していないなら、それは比較して初めて見える欠陥である。

読んで確証を得られたなら blocking にしてよい。**確認できなかった場合のみ、確証なしとして non-blocking に留める。**

## 秘密情報

- ハードコードされた認証情報・APIキー・トークン
- ログ・エラーメッセージ・例外へ秘密情報や個人情報が流れていないか
- URLのクエリ文字列へ秘密情報を載せていないか（ログとリファラに残る）
- 設定ファイル・テストフィクスチャへ実鍵が混入していないか

これは差分だけで判定でき、かつ影響が大きい。**優先度が高い観点である。**

## 暗号とランダム性

- 乱数: セキュリティ用途に非暗号論的乱数（`Math.random`、`rand()`）を使っていないか
- パスワード保存: 高速ハッシュ（MD5, SHA-1, 素のSHA-256）を使っていないか
- 比較: トークン・署名の比較が定数時間か
- 自前実装の暗号処理

## その他

- リダイレクト先にユーザー入力を使っていないか（オープンリダイレクト）
- 外部URLへのリクエストにユーザー入力を使っていないか（SSRF）
- レート制限のない認証・課金・送信系エンドポイントの追加
- 依存パッケージの追加。名前が既知パッケージと1文字違いでないか

## 棄却してよい候補

以下は候補として挙がりやすいが、単独では blocking にしない。

- 理論上は存在するが到達経路を示せない脆弱性
- 既存コードに元からある問題で、当該差分が導入したものではないもの（言及するなら non-blocking かつ「差分外」と明記する）
- 攻撃者が既に同等の権限を持っている前提でしか成立しない問題
