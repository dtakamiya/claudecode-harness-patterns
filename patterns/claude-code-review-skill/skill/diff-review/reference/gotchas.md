## 初期エントリ

以下は設計段階で予測した典型例である。**実測されたものではない。** 実使用で確認され次第、根拠を添えて書き換える。

### G1. ガード節で排除済みの null 参照

直前の `if (x == null) return;` や早期returnによって、当該行では既に null が排除されている。候補を出したら**同一関数内の上流を必ず読む**。

棄却理由の書き方: 「`foo.ts:31` のガード節で null が排除されるため到達不能」

### G2. 単一スレッドからしか到達しない競合状態

共有可変状態に見えても、呼び出し元がリクエストごとのインスタンス、単一のイベントループ、初期化時の1回限りの実行に限定されている場合がある。**呼び出し元を確認せずに競合状態を blocking にしない。**

棄却理由の書き方: 「`main.ts:12` から初期化時に1回のみ呼ばれるため競合しない」

### G3. 意図的な挙動を欠陥と誤認する

コメント・テスト・コミットメッセージが当該挙動を意図として明示している場合がある。典型例は、意図的にリトライしない設計、意図的に例外を握りつぶす設計、レガシー互換のための分岐。

SKILL.md Step 2（変更意図の推定）を飛ばすとこれが起きる。

棄却理由の書き方: 「`retry_test.ts:44` が『失敗時に再試行しない』ことをテストしており、意図された挙動」

### G4. 割り切れる値で書かれた失敗シナリオ

境界の指摘に対し、失敗シナリオが実際には失敗しない値になっている。`total=10, per_page=10` では `ceil` と `floor` が一致する。

**失敗シナリオは算術的に検算する。** 検算して失敗しないなら、その指摘は棄却する（欠陥がないか、原因の理解が誤っている）。

### G5. 差分外の既存コードへの指摘

差分が導入した問題ではなく、元からあるコードの問題。指摘自体が正しくても、レビュー対象を外れている。

述べる場合は `non-blocking` かつ「差分外」と明記する。blocking にしない。

### G6. リポジトリの既存スタイルへの指摘

周辺コードと同じ書き方をしているコードを保守性で指摘するもの。差分の周辺を読めば棄却できる。
