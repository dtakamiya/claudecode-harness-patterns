# 保守性

**この観点はほぼ常に non-blocking である。** 保守性の指摘が blocking になるのは、放置すると近い将来に正当性の欠陥を生むと具体的に説明できる場合に限る。

保守性は偽陽性の最大の発生源である。「こう書いた方が綺麗」は指摘ではなく好みであり、報告に載せない。SKILL.md Step 4の「具体的な失敗シナリオを書けるか」を、ここでは「**具体的な保守上の失敗を書けるか**」と読み替えて適用する。

## 報告してよいもの

以下は具体的な帰結を示せるため報告できる。

- **同一の判断が複数箇所へ複製されている**: 片方だけ更新される事故が起きる。どの2箇所かを示すこと
- **命名が実際の挙動と食い違う**: `validateUser` が検証に加えて保存もしている等。誤用を誘発する
- **エラーメッセージが原因の特定に使えない**: 障害時に調査が進まない
- **公開インターフェースの破壊的変更が、呼び出し側の更新を伴っていない**: これは正当性の問題でもある。差分内に呼び出し側が含まれるか確認する
- **テストが変更された挙動を検証していない**: 追加された分岐にテストがない、テストがアサートなしで通る、テストが実装をそのまま写している
- **削除されるべき死んだコードが残っている**: 当該差分が到達不能にした箇所

## 報告しないもの

- 命名の好み（`getUser` vs `fetchUser`）
- 関数の長さ、ファイルの長さ、ネストの深さ そのもの
- コメントの不足一般。ただし「意図が読めないと誤用される具体的な箇所」は別
- 抽象化の不足。**呼び出し箇所が2箇所の重複は、多くの場合そのままでよい**
- リポジトリの既存スタイルに従っているコード。周辺コードと同じ書き方なら指摘対象ではない
- リンタ・フォーマッタが機械的に指摘する事項（SKILL.md Step 1で既に実行されている前提）

## 判断の指針

差分の周辺コードを読み、**そのリポジトリの既存の書き方**を基準にする。一般論としての「良いコード」ではない。周辺と同じ書き方をしているコードを保守性で指摘するのは、ほぼ常に偽陽性である。
