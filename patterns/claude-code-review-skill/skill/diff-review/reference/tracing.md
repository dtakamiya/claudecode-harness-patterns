# 差分の外側を読む

差分だけでは判定できない欠陥がある。設計書 §2.4 が「2つ目のファイルを読まないと見えない」と述べるカテゴリで、認可漏れ、API契約違反、呼び出し規約の不整合がこれにあたる。

**これは全体走査ではない。** 差分に現れた識別子を起点に、その参照だけを引く。パス配下やリポジトリ全体を舐めるのは対象確定の規律に反する（SKILL.md Step 1）。

## 何を起点に、何を読むか

| 差分中の変更 | 読むもの | 探し方 |
|---|---|---|
| 関数・メソッドのシグネチャ変更（引数の増減・順序・型） | 全呼び出し元 | 関数名で Grep。差分外に未更新の呼び出しが残っていないか |
| 公開API・エクスポート・型定義の変更 | 参照箇所 | シンボル名で Grep。破壊的変更の波及範囲 |
| 新規エンドポイント・ハンドラの追加 | 同種の既存ハンドラ1件 | 認証・認可の適用方法が既存と揃っているか |
| 定数・設定値・フラグの変更 | その値の全参照箇所 | 定数名で Grep。前提を置いている箇所がないか |
| DBスキーマ・マイグレーション | 該当テーブルを触るコード | 列名・テーブル名で Grep |
| エラー型・例外クラスの変更 | catch/rescue している箇所 | 型名で Grep |

## 認可の確認手順

新規または変更されたエンドポイントについては、以下の順で読む。

1. そのハンドラ自身に認可チェックがあるか
2. 無ければ、ルーティング定義かミドルウェア定義を読む（差分外でも読む）
3. 同種の既存エンドポイントを1件読み、適用方法を比較する

**3の比較が最も有効である。** 既存の全ハンドラが `requireAuth` を通しているのに新規の1件だけ通していないなら、それは差分だけでは見えず、比較して初めて見える欠陥である。

## 読んだ結果の使い方

探索は**反証の材料**である。両方向に働く。

- **採用側**: 呼び出し元を確認して初めて「差分外に未更新の呼び出しが1件ある」と確証でき、`failure_scenario` が書ける
- **棄却側**: 全呼び出し元が更新済みだと分かれば、その候補は棄却できる

## 読めなかった場合

コードベースが大きい、識別子が一般的すぎて Grep が絞れない、といった理由で確認できないことがある。

そのときは**確認できなかった旨を報告に書く**。「呼び出し元を網羅的に確認できていないため確証なし」と述べるのは、確証のない指摘を blocking で出すよりも有用である。深刻度は non-blocking に留める。
