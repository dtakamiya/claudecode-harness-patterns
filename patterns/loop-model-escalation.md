# Loop Model Escalation

## 1. 目的と適用範囲

本規約は、無人ループの各試行でどのモデルとeffortを使うかを定める。役割ごとにモデルを固定せず、作業の種類に応じた安い段から始め、決定論的な検証に落ちたときだけ1段上げる。

成功の判定と再試行の上限は[Loop Guard Policy](loop-guard-policy.md)、項目の状態と試行回数は[Loop State Handoff](loop-state-handoff.md)を正本とする。本規約はそれらを変えず、「再試行のときに何を変えるか」を決める。

適用対象は、`verify`（決定論的な検証）を持つ項目を処理する無人ループである。検証を持たない作業は、どの段で通ったかを判定できないため対象外とする。

## 2. 観測した問題と根拠

### 2.1 観測

[Loop Guard Policy](loop-guard-policy.md)と同じ個人環境の定期実行基盤について、モデルの割り当て設定と利用量を2026-11-15に確認した。

| 観測 | 内容 |
|---|---|
| 割り当て方 | 役割・ジョブごとにモデルを固定する規則が16件ある（Opus 7、Sonnet 6、Haiku 3）。規則が無いものは既定のSonnet・effort mediumで動く |
| 失敗時の扱い | 検証に落ちてもモデルは変わらない。同じモデルでの再試行か、人間への報告になる |
| 利用量 | Claude Code全体の出力トークンのうち、Opusが約29%、Haikuが約4%を占める（ループ以外の手動利用を含む） |

割り当ては「その役割で最も難しい作業」に合わせて決まりやすい。そのため易しい項目にも上位モデルを使い、逆に難しい項目でも失敗後に段を上げる経路が無い。

### 2.2 根拠

本リポジトリの[Haikuモデル性能検証](../research/haiku-model-performance-validation.md)（Haiku 4.5とSonnet 4.5の比較）では、作業の種類によって差の出方が分かれた。

| 作業の種類 | Sonnetに対する相対スコア | 注意点 |
|---|---|---|
| 機械的な変換・定型修正 | 1.09 | なし |
| diffに限定したレビュー（反証ゲート付き） | 1.00 | なし |
| 探索・情報収集 | 0.97 | 3試行中1回で行番号を取り違えた。トークンはSonnetの2〜4倍 |
| 既存資料の読解と対比で答えが出る設計判断 | 1.00 | 白紙からの設計では3試行中2回で依頼の範囲を超えた |

安いモデルで十分な作業は多い。ただし種類によって失敗の仕方が違うため、始める段を作業の種類で決め、失敗を検証で捕まえて段を上げる。

## 3. 原則

1. **始める段は作業の種類で決める。** 役割やジョブの名前では決めない。
2. **段を上げるのは検証に落ちたときだけ。** [Loop Guard Policy](loop-guard-policy.md)の`FAILED`だけを契機にする。AIの「自信がない」という申告では上げない。
3. **上げるのは1回につき1段まで。** 試行回数の上限は既存の規約のまま（1回の再試行）とし、段の数で試行を増やさない。
4. **上げても直らない失敗では上げない。** `TIMED_OUT`、`BUDGET_EXCEEDED`、`RATE_LIMITED`、`killed`はモデルの能力の問題ではないため、段を上げずに既存の規則で扱う。
5. **段は記録して見直す。** どの段で通ったかを記録し、週次で始める段を調整する。

## 4. 段の定義

### 4.1 段

| 段 | モデル | effort |
|---|---|---|
| L1 | Haiku | low |
| L2 | Sonnet | medium |
| L3 | Opus | medium |

- effortを上げることを独立した段にしない。effortを上げてもモデルに無い能力は付かず、段が増えるほど試行回数の上限と合わなくなるためである。
- `high`以上のeffortは無人ループの既定では使わない。

### 4.2 作業の種類と始める段

| 作業の種類 | 始める段 | 再試行の段 | 検証で特に見るもの |
|---|---|---|---|
| 機械的な変換・定型修正 | L1 | L2 | 変換結果のschema、差分の範囲 |
| diffに限定したレビュー | L1 | L2 | 指摘のschema、指摘したファイルと行が差分の中にあるか |
| 結論だけでよい調査・分類 | L1 | L2 | 出力のschema、必須項目 |
| 位置を特定する探索（`file:line`を返す） | L1 | L2 | 返した`file:line`をスクリプトが実在確認する |
| 仕様が決まった実装・バグ修正 | L2 | L3 | test・typecheck・lint |
| 既存資料の対比で決まる判断 | L2 | L3 | 結論の欄と根拠の参照先が実在するか |
| 白紙からの設計、原因不明の不具合 | 無人ループでは扱わない | — | `proposed`のまま人間へ渡す |

- 位置を特定する探索は、行番号の取り違えを検証で捕まえられることを条件にL1から始める。スクリプトが`file:line`を確かめられない場合はL2から始める。
- 既存資料の対比で決まる判断は、上記の検証ではHaikuでも相対スコア1.00だった。ただし試行が1タスク3回と少なく、検証で結論の正しさまでは確かめられないため、L2から始める。6章の記録が溜まったらL1を試す。
- 項目の種類は、[Loop State Handoff](loop-state-handoff.md)の項目に`kind`として持たせる。`kind`が無い項目はL2から始める。

## 5. 試行の流れ

1. スクリプトが項目の`kind`と`attempts`から段を決める。初回は始める段、2回目（再試行）は再試行の段を使う。
2. `claude -p --model <モデル> --effort <effort>`で子を起動する。
3. 検証に落ちて`FAILED`になったら、[Loop State Handoff](loop-state-handoff.md)の規則で`todo`に戻す。次の試行では1段上の段を使う。
4. 再試行の段でも落ちたら`blocked`にする。それより上の段は自動では試さない。人間が原因を見て、`kind`の付け直し、項目の分割、始める段の変更のいずれかを行う。

再試行で段を上げるときは、新しいセッションで始める。下の段の会話を引き継がず、次の3つだけを渡す。

- 項目（`id`、`title`、`acceptance`）
- 引継ぎメモ
- 落ちた検証の出力

`--fallback-model`はモデルの過負荷や利用不可のときに切り替える仕組みであり、品質による段の引き上げとは別物である。段の引き上げには使わない。

### 5.1 大量の項目をまとめて処理する場合

分類や定型修正のように項目が多い場合は、まず全件を始める段で処理し、検証に落ちたものだけを次の段で処理し直す。1件ずつ段を上げながら進めるより、安い段で通る分の費用を最小にできる。

## 6. 記録と見直し

[Loop Guard Policy](loop-guard-policy.md)5章の実行記録には`model`と`effort`の欄がある。これに`tier`（L1〜L3）と`kind`を加え、週次で次を見る。

| 指標 | 見直しの目安 |
|---|---|
| 作業の種類ごとの、始める段での`VERIFIED`率 | 2週間続けて50%を下回ったら、その種類の始める段を1段上げる |
| 作業の種類ごとの、再試行の段での`VERIFIED`率 | 始める段とほぼ同じなら、段を上げても直らない失敗である。項目の切り方か検証を見直す |
| `VERIFIED` 1件あたりの費用（種類別） | 段の調整の前後で比べる |

始める段をL2にした種類で、L2の`VERIFIED`率が十分に高い場合は、項目の1割程度をL1で試し、下げられるかを確かめる。

モデルやClaude Codeの版を上げたら、4.2の表を見直す。表の始める段は、[Haikuモデル性能検証](../research/haiku-model-performance-validation.md)を行った時点のモデルに基づいている。

## 7. 段階導入

1. **記録だけ**: 既存の割り当てのまま、実行記録に`kind`と`tier`を加える。
2. **再試行での引き上げ**: `FAILED`の再試行だけ1段上げる。始める段は変えない。
3. **始める段の引き下げ**: 4.2の表でL1から始める種類について、項目の一部をL1で試し、`VERIFIED`率を記録と比べる。
4. **役割ごとの固定の撤去**: 始める段を作業の種類で決める方式に切り替え、役割・ジョブごとのモデル固定を外す。
