# Jira インシデントレビュースキル Eval

[設計書 §6](../docs/design.md) で定めた評価タスクの定義です。

## ファイル

- `tasks.jsonl` — 評価タスク 16 件。1 行 1 タスクの JSON Lines 形式。各タスクは
  `ticket_body`（貼り付ける想定のチケット本文）を含み、code-based タスクは
  `grader_keywords` を持ちます。

## 前提

**実行基盤は含みません。** Agent Skills の eval を実行する組み込みの仕組みは現時点で
存在せず、利用者が独自の評価システムを構築する必要があります。`tasks.jsonl` は仕様で
あり、実行スクリプトは別途要ります。

## 設計方針

[Demystifying evals for AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents) に従います。

- **良いタスク**とは「2 人のドメイン専門家が独立に同じ pass/fail へ到達するもの」
- **経路ではなく成果物を採点する** — 手順の遵守ではなく報告内容を評価する
- **正例と負例の両方**を置く — 偽陽性タスク（T1/T8/T11/T12/T15）が「粗探し・萎縮を
  しない」ことの実測に不可欠
- **各タスクを複数回試行する** — 1 回の結果で判断しない
- **pass rate 0% はタスクの故障を疑う**

## タスク一覧

| ID | 種別 | grader | 測定対象 | 狙い |
|---|---|---|---|---|
| T1 | 正例 | model | 過剰指摘の抑制 | 良いインシデントチケットでブロッカー 0、無根拠な要改善なし |
| T2 | 正例 | code | 検出 | タイムライン欠落・proximate 停止・曖昧なアクションを検出 |

| T4 | 正例 | model | 種別分岐 | 良いバグチケットでバグチェックリストを適用、ブロッカー 0 |
| T5 | 正例 | code | 検出 | 再現手順なし・severity/priority 混同を検出 |
| T6 | 正例 | model | プロセスの穴 | 「今後は周知」だけの再発防止 + 最深層と対策の非接続を指摘 |
| T7 | 正例 | model | 種別曖昧 | 曖昧なチケットで両視点の講評を出す |
| T8 | 負例 | model | precision | 良いチケットへの不備指摘に本文引用があるか |
| T9 | 負例→検出 | model | 浅い深掘り | 5 Whys を 5 段書いたが単線で Why5 が「担当者の考慮漏れ」→ 要改善〜ブロッカー |

| T12 | 正例 | model | 偽陽性 | 小規模・単一要因が妥当なインシデント → C3 を機械的に要改善にしない |
| T13 | 正例 | model | 種別判定 | SEV 表記なし・顧客影響が言外 → インシデントと判定し根拠を述べる |
| T14 | 正例 | model | 個数 | アクションアイテム 5 件 → 「真因を絞れていない可能性」を添える |
| T15 | 正例 | model | 偽陽性 | 実名入り中立タイムライン行 + 根本原因はシステム主語 → blameless 指摘ゼロ |
| T16 | 負例→検出 | model | blameless washing | 文言は完璧にシステム主語だが分析が proximate 止まり → C2/second story で要改善 |

**T6 が最重要です。** Webリサーチが一致して指摘する通り、ポストモーテムの価値は
アクションアイテムの実効性で決まります。「周知する」で閉じる再発防止と、「根本原因は
深いのに対策がその深さに接続していない」ケースを検出できることが、本スキルの存在意義です。

**T9 / T16 は「深掘りの体裁だけ整った」ケースを弾けるかを測ります。** T9 は単線 5 Whys、
T16 は blameless washing。どちらも C1〜C2 / second story チェックの実効性を測る負例です。

**T1 / T8 / T11 / T12 / T15 は precision と萎縮対策の裏側です。** 網羅方針（全項目に
合否）の代償は「粗探し」と「答案採点的なトーンによる萎縮」。良いチケットに無根拠な
「要改善」を積み上げていないか、5 Whys 形式でない深い根本原因を弾いていないか、小規模で
単一要因が妥当なケースを機械的に叩いていないか、実名タイムライン行を非難認定していないか
を測ります。

**T13 は種別判定の「細い橋」を測ります。** SEV 表記など明示的な手がかりがなく、
「本番で」「先週リリース」から推論を要するケースでインシデントと判定できるか。

## grader の選択と grader_keywords

コードベースを優先し、機械判定できない部分だけモデルベースへ回します。**否定形・不在の
確認**（「〜を要求していない」「粗探しをしていない」）はキーワード不在では判定できない
ため model-based にします（T4 は当初 code-based だったが model-based へ変更）。

### code-based タスクの `grader_keywords`

各 code-based タスク（T2, T5）は次の構造を持ちます。

```json
"grader_keywords": {
  "must_all": [
    ["TTD", "検知時刻", "検知までの時間"],
    ["proximate", "近接原因", "Why3 で止ま", "掘り下げ"],
    ["すり抜け", "テストのレイヤ", "どのテスト"],
    ["owner", "担当者", "所有者"],
    ["期日", "due", "デッドライン"]
  ],
  "blocker_count_min": 3
}
```

- `must_all` の各内側配列は「いずれか 1 つが報告に出現すれば可」（OR）。配列全体で AND。
- `blocker_count_min` / `blocker_count_max`: 「ブロッカー N 件」の N を数値抽出して
  期待範囲と突き合わせる。
- 日本語出力の表現揺れに弱いため、揺れが本質的な項目（hindsight bias、second story 等）は
  code-based に残さず model-based へ。

### 「無根拠な要改善」の操作的定義（T1/T8/T11/T12 で使う）

必須項目チェック表で「要改善」とされた各行について、根拠列が (a) 本文の引用、
(b)「記載なし」のいずれかであること。それ以外の理由（「もっと詳しく書けるはず」
「一般にはこうすべき」）が付いた要改善が 1 件でもあれば fail。これは code-based で
判定できる。

### T6 の部分点ルーブリック

T6 の `expected_behavior` は「必須 3 項目 + 加点 5 項目」に分かれます。

- **必須（この 3 つが揃えば pass）**: (1) 再発防止が「周知」止まりで恒久的でないと指摘、
  (2) 顧客報告検知なのにアラート追加がアクションアイテムにないことをブロッカー指摘、
  (3) 根本原因の最深層（単一設定ソースの欠如）に対策が対応していない不整合を指摘
- **加点**: owner がチーム名、期日が「今週中」、回帰テストなし、副作用未検討、
  「注意書き追加」を一過性と分類

## 記録する指標

| 指標 | 算出 | 位置づけ |
|---|---|---|
| プロセスの穴の検出率 | T2, T6, T9, T10, T16 での該当指摘率 | **主目標** |
| 過剰指摘率 | T1, T8, T11, T12, T15 での無根拠な「要改善」の割合 | 0 に近づける |
| 良いチケットでの要改善率 | over-flagging タスクの「必須項目チェック表の要改善行数 / 総行数」 | 参考（無根拠 0 が最重要） |
| 種別判定の正解率 | T4, T7, T13 での分岐の正しさ | 全試行で遵守 |
| blameless 言い換えの質 | T3 で引用（実名伏せ）+ システム主語の言い換え + second story チェックが揃っているか | 全試行で存在すべき |
| コードレビュー誤帰属の不在 | すり抜け工程・再発防止でコードレビューを挙げていないか | 全試行で遵守 |
| 編集の不実行 | Edit / Write を呼んでいないか | 全試行で遵守 |

## モデル横断テスト

公式は「使う予定のすべてのモデルでテストせよ」と述べます。特に **Haiku** で次を確認:

- Step 3（QA/QC 観点）が省略されないか
- Step 5（blameless スキャン）が「該当なし」で素通りしていないか、second story チェックを飛ばしていないか
- C1〜C8 の判定が「システムという語のマッチ」に退化していないか（対比例を参照しているか）

## 拡張

初期セット 16 件は出発点です。実使用で誤検出・見逃しが出るたびに、そのパターンを
`reference/false-positives.md` に 1 件、`tasks.jsonl` に 1 件足してください（Ratchet
パターン）。実際の（匿名化した）ポストモーテムを題材にすると、想定で作った本文より
鋭くテストできます。
