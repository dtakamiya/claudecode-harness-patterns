# jira-incident-review スキル実装

[設計書](../docs/design.md)に従った実装本体です。任意の環境へコピーして単独で動作します。
Jira への接続は行わず、**貼り付けたチケット本文**だけを見ます。

## 導入

`jira-incident-review/` ディレクトリをスキル配置先へコピーします。

```bash
cp -r jira-incident-review ~/.claude/skills/          # personal（全プロジェクトで有効）
cp -r jira-incident-review <repo>/.claude/skills/     # project（当該リポジトリのみ）
```

`/jira-incident-review` で起動し、続けてチケット本文（説明・コメント・フィールド）を
貼り付けます。URL だけでは動きません（本文の貼り付けを求めて停止します）。

## 構成

```text
jira-incident-review/
├── SKILL.md                    # 本体（Step 1〜6、免責文・想定利用者・判定値対応表を含む）
└── reference/                  # 各 Step で該当するものだけ読まれる（先読みしない、1階層）
    ├── incident-checklist.md   # 本番インシデント用（時刻定義/必須/タイムライン/根本原因 C1〜C8＋対比例/影響/遅延要因）
    ├── bug-checklist.md        # 開発時の障害用（記述の質/トリアージ/原因 C1a・C1b/QA）
    ├── qa-process.md           # QA/QC 観点（障害分類・検知経路・すり抜けたテストのレイヤ・再発防止の実効性・回帰テスト・副作用）※重点
    ├── blameless-language.md   # 非難的表現の検出＋言い換え＋second story チェック＋許容表現
    ├── action-items.md         # アクションアイテムの 7 軸判定＋カバレッジ
    └── false-positives.md      # 実測された誤検出・過剰指摘パターン（Step 6 で照合、Ratchet で育てる）
```

## 配布形態の制約

`when_to_use` / `argument-hint` / `disallowed-tools` / `model` は **Claude Code 専用フィールド**です。
Agent Skills spec 外のフィールドを含むため、**claude.ai へのアップロード、Skills API、
`package_skill.py` では失敗します**（無視されるのではなくハードエラー）。

これは意図した割り切りです。詳細は[設計書 §4.2.1](../docs/design.md)。
なお、チケット不可侵は「Jira 書き込み手段を持たせない」（MCP なし・Bash なし）ことで
担保しており、`disallowed-tools` はローカルファイル保護とレビュアーロールの宣言です。

## 設計の要点（詳細は設計書）

| # | 要点 |
|---|---|
| 1 | **プロセスの穴を重く見る** — すり抜けたテストのレイヤが未特定・再発防止が「周知」止まり・最深の原因に対策が紐付かないならブロッカー |
| 2 | **コードレビューをすり抜け工程にしない** — レビューは欠陥検出の手段ではない（Microsoft Research）。TDD の前提では欠陥検出はテストの責務 |
| 3 | **網羅方針＋萎縮対策** — 全項目に合否。ただし免責文・「良い点」先出し・「要改善」の内訳表示 |
| 4 | **推測で非難扱いしない** — blameless 指摘とアクションアイテムの不備指摘は本文の引用に限る（実名は伏せる）。言い換えだけで終わらせず second story まで見る |
| 5 | **種別で分岐** — インシデント / バグを判定し片方だけ読む。曖昧なら両視点。Step 2 で「該当なし」多数なら再判定 |
| 6 | **編集しない** — Jira 書き込み手段を持たせないことで担保。出力は「作成者の自己追記用の下書き」まで |

## 検証済みの挙動

`evals/tasks.jsonl` のサンプル本文で確認する想定挙動です（実行基盤は同梱しません）。

| 入力 | 期待 |
|---|---|
| URL のみ | 本文の貼り付けを求めて停止 |
| 良いインシデントチケット | ブロッカー 0、各項目おおむね合格、無根拠な要改善なし |
| タイムライン欠落・proximate 停止・曖昧なアクション | 該当をブロッカーとして検出 |
| 「今後は周知する」だけの再発防止 | 「恒久的なプロセス組み込みでない」と指摘 |
| 5 Whys を 5 段書いたが単線で「担当者の考慮漏れ」着地 | 「単線 + 実質人間非難」を要改善〜ブロッカー |
| 「レビューで見落とした」を根本原因/すり抜け工程にしている | それ自体を要改善、テスト欠如への書き換えを促す |
| 文言はシステム主語だが分析が proximate 止まり | second story チェックで要改善 |
| 実名入り中立タイムライン行 + 根本原因はシステム主語 | blameless 指摘ゼロ |
| 外部依存（クラウド障害）で「すり抜け工程」がない | ブロッカーにしない（障害分類 (d)） |
| 実名 + 「〜し忘れた」 | 引用（実名伏せ）とシステム主語への言い換え案を提示 |
| 良いバグチケット | バグチェックリストを適用、ブロッカー 0 |
| 種別が曖昧なチケット | インシデント / バグ両方の視点で講評 |

## 改善の回し方

実使用で誤検出・見逃しが出たら次のように 1 件ずつ足します（設計書の Ratchet パターン）。

1. 判定基準の追加なら、該当する `reference/*.md` に 1 行追記
2. 偽陽性・過剰指摘なら、`reference/false-positives.md` に 1 件追記（Step 6 で照合される）
3. いずれも `../evals/tasks.jsonl` に対応するタスク（正例 / 負例）を 1 件追加
