# アクションアイテムの判定基準

Step 4 で使う。チケット内の各アクションアイテム / follow-up を個別に採点する。
**本文に該当箇所が引用できるものだけを不備として指摘する**（無い項目の推測はしない）。

出典: incident.io（Specific / Owned / Due-dated / Prioritized の 4 属性、
mitigative vs preventative）、Rootly（検証方法）、Atlassian（work item へのリンクと
追跡、最大 3 件の目安）、Google SRE Book（アクションアイテムの適切さと優先順位）。

## 目次

- 7 つの判定軸（1 Specific / 2 Owned / 3 Due / 4 分類 / 5 検証 / 6 追跡 / 7 クラス有効性）
- カバレッジ（アクションアイテム群 全体の評価）
- 個数の目安
- 出力（SKILL.md の表に対応）

---

## 7 つの判定軸

### 1. Specific（具体性）

具体的なシステム変更になっているか。

- OK: 「チェックアウト API のエラー率が 2% を 5 分超えたら PagerDuty に通知するアラートを追加」
- OK: 「決済ワーカーに 100 req/s のレート制限を追加」
- NG: 「モニタリングを改善する」「エラーハンドリングを見直す」「レジリエンスを高める」

### 2. Owned（所有者）

**個人名**が付いているか。チーム名は不可（誰も動かない）。

- OK: 「担当: 山田」
- NG: 「担当: 決済チーム」「担当: SRE」「担当: 未定」

### 3. Due-dated（期日）

具体的な期日があるか。

- OK: 「YYYY-MM-DD 形式の具体的な暦日」「次スプリント終了（具体日を併記）まで」
- NG: 「近日中」「Q3 中」「ASAP」「優先度が上がり次第」

### 4. 分類（detective / mitigative / preventative / corrective が明示されているか）

対策の**種類**が区別されているか。混在してよいが、どれなのかが分かること。

| 種類 | 意味 | 例 |
|---|---|---|
| detective | 次に起きたとき**早く気づく** | エラー率アラート追加、SLO バーンレート監視、キュー滞留数の監視 |
| mitigative | **この特定の穴**を塞ぐ | この設定値にバリデーションを追加、この API にレート制限を追加 |
| preventative | **同じクラスの障害**に対処する | 全設定値をスキーマ検証する仕組み、全外部呼び出しを共通リトライラッパ経由に |
| corrective | **今回の後始末** | 滞留データの再送、不整合レコードの修正 |

**「アラート追加」は detective であって preventative ではない**。detective だけを
preventative と称している場合は分類 ×。分類が全く無ければ ×。

### 5. 検証（完了の確認方法）

「これができたら完了」の判定方法が書かれているか。

- OK: 「ステージングで意図的にエラー率を上げ、5 分以内に通知が飛ぶことを確認する」
- OK: 「#1183 相当の変更を入れると CI が落ちることを再現する」
- NG: 記述なし（「やった」だけで閉じられる）

### 6. 追跡（work item 化）

独立した Jira issue / タスクにリンクされ、この PIR チケットが閉じても追えるか。

- OK: 「#PROJ-1234」
- NG: ポストモーテム本文の箇条書きに書かれているだけ（チケットクローズで流れる）

### 7. クラス有効性（このアクションアイテムは再発を実際に防ぐか）

このアクションアイテムが完了したとき、**同じ最深の contributing factor（＝
incident-checklist.md C7 で特定した systemic cause）による再発**は実際に防がれるか。

- 防がれる（preventative がその原因に対応している）→ ○
- 防がれない（detective で早期検知になるだけ、mitigative でこの 1 箇所だけ塞ぐだけ）
  → ×。この場合、**別途 preventative なアクションアイテムが必要**である旨を指摘する。

例: 根本原因が「接続プールの枯渇（＝共通の接続取得ヘルパを経由しない実装が通る）」
なのに、アクションアイテムが「決済 API のエラー率アラートを追加」だけ → 7 軸のうち
1〜6 が ○ でも、クラス有効性 ×（症状を早く知らせるだけで、次に別の箇所で同じことが
起きる）。

## カバレッジ（アクションアイテム群 全体の評価）

根本原因分析で特定された contributing factors を列挙し、各々に対応するアクション
アイテムがあるかを突き合わせる。

| contributing factor | 対応するアクションアイテム | 判定 |
|---|---|---|
| <factor 1> | <AI #NNN、または「なし」> | ○ / 空欄 |
| <factor 2> | ... | ... |

- 空欄がある factor → 要改善。
- **その factor が最深（＝そこを直さなければ再発する）で、対応アクションアイテムが
  無い → ブロッカー**（incident-checklist.md C7 と対）。
- 逆に、1 つの factor に 3 件集中して他の factor が放置されている場合も要改善
  （バランスを欠く）。

---

## 個数の目安

1 つのポストモーテムでアクションアイテムが **4 件以上**あれば、
「真因を絞れていない可能性」を一言添える（Atlassian の目安は最大 3 件。
多すぎるのは、本当に効く 1〜2 手を特定できていないサイン）。

ゼロ件は論外（**ブロッカー**）。「対応不要」で閉じるなら、その判断根拠が要る。

## 出力（SKILL.md の表に対応）

| 項目 | Specific | Owned | Due | 分類 | 検証 | 追跡 | クラス有効性 | 総合 |
|---|---|---|---|---|---|---|---|---|
| <アクションアイテムの引用> | ○/× | ○/× | ○/× | ○/× | ○/× | ○/× | ○/× | 合格 / 要改善 / ブロッカー |

- **Owned または Due が × のアクションアイテム**は、それだけで総合「ブロッカー」
  （SKILL.md のブロッカー基準に該当）。
- クラス有効性 × は「要改善」（別の preventative が必要、と講評に書く）。
- ○/× は各軸の充足を表す簡易記号で、必須項目チェック表の 3 値（合格 / 要改善 /
  該当なし）とは別の体系。総合列の 3 値だけが必須項目チェックと揃う。
