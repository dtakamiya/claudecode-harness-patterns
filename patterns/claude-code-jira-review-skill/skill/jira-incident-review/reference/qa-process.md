## 0. まず障害の性質を分類する

「すり抜け工程」（§2）を問えるのは **実装バグ**の場合だけである。障害を次に分類し、
以降の問いを使い分ける。

| 分類 | 例 | §2 で問うもの |
|---|---|---|
| (a) 実装バグ | コードの欠陥、ロジック誤り、境界条件漏れ | どの**テストのレイヤ**（unit / integration / E2E / 型 / lint / staging / canary）をすり抜けたか。**コードレビューは含めない**（下の注記） |
| (b) 設計上の欠陥 | リトライ方針の不在、単一障害点、密結合 | この設計判断が設計レビュー / ADR / 設計ドキュメントで検討される機会はあったか。設計上の前提（例: 外部依存は劣化するもの）が置かれていたか |
| (c) キャパシティ | プール枯渇、ディスク満杯、レート超過 | 容量計画・負荷予測のプロセスがあるか。閾値監視・自動調整があるか |
| (d) 外部依存 | クラウド/SaaS の障害、上流 API の劣化 | 外部依存の劣化を前提とした設計（タイムアウト・リトライ・フォールバック・サーキットブレーカ）になっているか。**「すり抜け工程」は問わない** |
| (e) 組織・プロセス | 要件の伝達漏れ、意思決定の記録なし、引き継ぎ失敗 | 要件・意思決定が明文化される仕組みがあるか。伝達経路が定義されているか |

複数にまたがる障害もある（例: プロバイダ劣化(d) が引き金だがリトライ設計の欠如(b) が
被害を広げた）。その場合は各分類の問いを両方あてる。

**判定の指針**: 分類 (a) で「すり抜けたテストのレイヤが 1 つも特定されていない」→ ブロッカー。
分類 (b)〜(e) で「対応する上の問いに 1 つも答えていない」→ ブロッカー。
分類 (d) の障害に「テストがなかった」を要求してはならない（false-positives.md FP6）。

### コードレビューをすり抜け工程の原因にしない

「コードレビューで気づけなかった」を根本原因やすり抜け工程として書いているチケットは、
**それ自体を要改善**とする。理由:

- コードレビューの主目的は保守性・可読性・知識移転であって欠陥検出ではない。
  実測でもレビューコメントの約 15% しか欠陥に関係せず、約 80% のレビューはバグを
  見つけない（Microsoft Research "Code Reviews Do Not Find Bugs"、Google の分析）。
- レビューに欠陥検出を期待する設計自体が誤り。TDD / shift-left の前提では、その不具合を
  捕らえる**テストが存在すべきだった**。「レビューで見落とした」は、本来「この条件を
  検証するテストが無かった / 不十分だった」と書かれるべきもの。
- レビューが関わるのは **「テスト追加の要否がレビューや CI で可視化・強制される
  仕組みがあったか」というプロセス設計**の側面だけ。「レビュアーが注意すべきだった」
  ではなく「テストの不足がゲートで検出されなかった」に置き換えさせる。

言い換えの例:
- 「レビューで接続方式の問題を見落とした」→「接続数・プール使用率を検証するテストが
  CI に無く、この変更クラスがゲートを通過した」
- 「レビュアーが在庫係数の欠落に気づかなかった」→「在庫 0 のケースを検証するユニット
  テストが無く、リファクタで係数が消えても CI が落ちなかった」

## 1. 検知経路

チケットから「どうやってこの障害に気づいたか」を読み取る。

| 検知経路 | 評価 |
|---|---|
| 監視アラート / SLO バーンレート / 自動ヘルスチェック | 合格 |
| 社内メンバーが偶然発見 | 要改善（監視の穴。アラートを追加すべき対象） |
| 顧客からの問い合わせ / SNS | 要改善（監視の穴。かつ検知が遅れている可能性大） |

顧客報告で検知したのに「アラート追加」がアクションアイテムに無ければ **ブロッカー**。

## 2. すり抜け工程の特定（§0 の分類に応じて問う）

分類 (a) 実装バグの場合、「この不具合はどの**テストのレイヤ**を通過して本番/対象
環境に到達したか」がチケットに書かれているかを見る。少なくとも次のどれを通過したかに
言及があること。

- ユニットテスト（該当するテストが無かった / あったが不十分だった）
- 結合テスト / E2E
- 静的解析 / 型検査 / lint / CI チェック
- ステージング / QA 環境での検証
- カナリアリリース / 段階的ロールアウト

**コードレビューはこのリストに含めない**（上の注記「コードレビューをすり抜け工程の
原因にしない」を参照）。

**分類 (a) ですり抜けたテストのレイヤが1つも特定されていない → ブロッカー。**
「テストが無かった」だけでも可だが、「なぜ無かったか（気づかれなかったのか、
コスト判断で省いたのか、要件が明文化されていなかったのか）」まであると合格。

分類 (b)〜(e) の場合は §0 の表の右列の問いに答えているかを見る。

## 3. 再発防止の実効性

アクションアイテム / follow-up を「品質プロセスへの恒久的な組み込み」かどうかで分類する。

| 分類 | 例 | 評価 |
|---|---|---|
| 恒久的な組み込み | 回帰テスト追加、アラート/SLO 追加、CI チェック追加、lint ルール追加、ガードレール（バリデーション・レート制限・確認ステップ）追加 | 合格 |
| 一過性 / 人依存 | 「チームに周知する」「今後は注意する」「気をつける」「再教育する」「ドキュメント / 手順書に一文（注意・確認すること）を足す」だけ | 要改善。これしか無ければ **ブロッカー** |
| 恒久だが未追跡 | 恒久策だが work item 化されず本文に埋もれている | 要改善（追跡されず流れる） |

**「レビューチェックリストに項目を追加」は、バグ再発防止策としては弱い**（人が毎回
チェックする前提で、レビューの欠陥検出率は低い）。それ**単独**なら一過性寄りとして
「その不具合を捕らえるテスト / CI チェックも併せて追加すべき」と指摘する。テスト等の
恒久策とセットなら、レビュー観点追加は補助として認めてよい。

判定の問い: **「同じ人が退職しても、この対策は残って機能するか」**。残らないなら一過性。

**「手順書の更新」の境界**: 既存フローに新しい**必須ステップを機械的に強制する**
（チェック無しでは先に進めない、ゲートで止まる）なら恒久。既存文書に「注意」
「確認すること」という**散文を足すだけ**なら一過性。
例: 「デプロイ手順書に『プロデューサとコンシューマ両方を確認すること』と注意書きを
追加」→ 一過性（人が読んで従う前提）。「キュー名の不一致を検出する CI チェックを追加」
→ 恒久。

**「CI を追加する」と書かれている場合**: その**内容**で恒久側に分類してよい
（実装が完了しているかは Step 4 の「追跡」で見る問題であって、ここでは対策の**種類**を見る）。

## 4. 回帰テスト

この特定の不具合を再発させないテストが定義されているか。

- 「この障害を再現するテストを追加した / 追加チケット #NNN」→ 合格
- 修正 PR に対応するテストがある旨の言及 → 合格
- 言及なし → 要改善。インシデントなら **ブロッカー**

## 5. 健全性メトリクスへの言及（あれば加点、無くても可）

- アクションアイテム完了率の目標（80%+ が目安。50% 未満は形骸化）
- この障害クラスの再発率（<5% が目安。30% 超はポストモーテムが機能していない）
- 過去の類似インシデントへの参照（再発なら、前回の対策がなぜ効かなかったか）

**「過去に同じ障害があった」と本文にあるのに前回対策の検証が無い → ブロッカー。**

## 6. 対策の副作用検査（How Complex Systems Fail Point 15）

「Post-accident remedies usually increase the coupling and complexity of the system」。
恒久策それぞれについて、次を一言問う。

- この対策は新たな依存・失敗点・運用負荷を増やさないか。
  - アラート追加 → アラート疲労（本当に対応が要るときに埋もれる）
  - デプロイ経路に検証ステップ追加 → デプロイの新たな失敗点・遅延
  - スキーマ検証の仕組み導入 → その仕組み自体の障害・メンテナンス
- 増やすなら、それを**許容する判断**がチケットにあるか（トレードオフを認識した上での
  選択か、無自覚か）。

副作用が検討されていない → **要改善（副作用未検討）**。ブロッカーにはしない
（対策自体は前進なので）。
