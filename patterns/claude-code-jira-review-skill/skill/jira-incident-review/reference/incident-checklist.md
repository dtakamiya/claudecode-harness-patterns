# 本番インシデント / ポストモーテム チェックリスト

Step 2 で使う。各項目に `合格 / 要改善 / 該当なし` を付ける。
情報が本文になく判定できない項目は「要改善（記載なし）」とする。
「記載なし」は原則として軽微指摘だが、**SKILL.md「ブロッカーの基準」に挙げた項目に
該当する「記載なし / 未特定」はブロッカーに昇格する**。

出典: Atlassian（Post-incident review best practices / Postmortems handbook）、
incident.io（SRE incident post-mortem best practices）、Rootly（Postmortem meeting guide）、
Kitchen Soap / John Allspaw（"The Infinite Hows" / 単一 root cause・hindsight bias・
counterfactual 批判）、Richard Cook「How Complex Systems Fail」、
Google SRE Book「Postmortem Culture: Learning from Failure」。

## 目次

- 時刻の定義（影響開始 / 検知 / 復旧）
- A. 必須フィールド（A1 severity 〜 A7 公開リードタイム）
- B. タイムライン（B1〜B6）
- C. 根本原因分析（C1 因果の深さ 〜 C8 後知恵の断罪）＋ 良い/悪い根本原因の対比例
- D. 影響評価（D1〜D6）
- E. 検知・対応の遅延要因（E1〜E3）

## 時刻の定義（A セクションの判定はこの定義で行う）

本スキルは **TTD / TTR / MTTR という語の揺れは問わない**。差の算出に必要な 2 つの
時刻が一意に特定できるかだけを見る。

- **影響開始時刻**: 顧客影響が実際に始まった時刻（デプロイ時刻とは限らない）。
- **検知時刻**: この事象に対する最初のシグナルの時刻。自動アラート発報、または
  人間の第一報のどちらでもよい。**どちらを採ったかがチケットから読めれば合格**。
  両者が乖離する場合は両方の記載が望ましい。
- **復旧時刻**: 顧客影響が実質的に終了した時刻（症状の消失）。滞留処理・再送・恒久
  修正が別途続く場合は、それを「影響終了後の残作業」として区別して書けていれば合格。
  影響終了と残作業完了が混在して復旧時刻が一意に読めない → 要改善。
- 検知時刻 − 影響開始時刻 = 検知までの時間（TTD 相当）。
  復旧時刻 − 影響開始時刻 = 復旧までの時間（TTR 相当）。

## A. 必須フィールド

| # | 項目 | 合格の目安 |
|---|---|---|
| A1 | severity / 重大度 | severity の値が明示され、かつチケット内に判断根拠（影響量・時間・顧客数）が併記されている。**値そのものの妥当性は組織の SEV 基準に委ね、ここでは判定しない**（1 枚のチケットからは判定できない） |
| A2 | 影響開始時刻 | タイムスタンプがある |
| A3 | 検知時刻 | タイムスタンプがある（上の定義参照） |
| A4 | 復旧時刻 | タイムスタンプがある（上の定義参照） |
| A5 | 影響範囲 | 影響を受けたサービス / 顧客セグメント / 地域が特定されている |
| A6 | インシデント指揮者 / 対応者 | 対応者が記載されている。役割ベース（IC、二次対応 等）が望ましいが、**実名でも可**。非難文脈での記名（「X の対応が遅かった」等）でないこと |
| A7 | 公開リードタイム | 解決後おおむね数日以内にドラフトされている（Atlassian の目安は 48 時間。組織の PIR 規約があればそれに従う）。作成日時と復旧時刻を比較し、明らかに放置（週単位）なら要改善 |

**A1・A2・A3・A4 のいずれか欠落 → ブロッカー**（検知・復旧までの時間が算出できない）。

## B. タイムライン

| # | 項目 | 合格の目安 |
|---|---|---|
| B1 | 検知フェーズ | 最初のアラート / 報告がタイムスタンプ付きで記載 |
| B2 | エスカレーションフェーズ | インシデント宣言・対応者招集の時刻 |
| B3 | 診断フェーズ | 調査の経緯・棄却した仮説が時系列で記載 |
| B4 | 緩和フェーズ | 影響を下げた措置とその時刻 |
| B5 | 解決フェーズ | サービス復旧確認の時刻 |
| B6 | 前向きな記述 | 復旧から逆算せず、インシデント前の時点から時間を進める形で書かれている（hindsight bias 回避、PagerDuty: foresight not hindsight） |

B3 が「原因はこれ、以上」と圧縮されている場合は要改善（診断の実際の経緯が失われている）。

## C. 根本原因分析

| # | 項目 | 合格の目安 |
|---|---|---|
| C1 | 因果の深さ | why の**本数**ではなく**到達点**で見る。最終的に「その事象を可能にした修正可能な機構 / プロセス」を名指しできているか。5 Whys を 5 段書いてあっても単線かつ「担当者の考慮漏れ」に着地するなら不足。why が 3 本でも、最終 Why が「設定を単一ソースから供給する仕組みがない」のように修正対象を名指ししていれば合格（下の対比例を参照） |
| C2 | proximate cause で止まっていない | 「〜が原因」で終わらず、その条件を生んだ仕組みまで辿っている |
| C3 | contributing factors が複数 | 「各々が必要だが単独では不十分」の形で複数挙がっている（複雑系の障害は単一原因では起きない、How Complex Systems Fail Point 3）。**ただし明確な単一要因で小規模（影響数分・SEV4 等）の障害は、単一でも妥当なら合格**。規模に照らして判断する |
| C4 | counterfactual が根本原因に無い | 「〜していれば防げた」「気づくべきだった」を原因として置いていない（それは後知恵） |
| C5 | 非難的表現が無い | C1〜C4 の本文に人名 + 過失動詞が無い（詳細は blameless-language.md、Step 5 で扱う） |
| C6 | why now（潜在要因の顕在化） | 「その条件はいつから存在し、なぜ今まで顕在化しなかったか」への言及がある（トラフィック増、他変更との合流、たまたま等）。latent condition は常に存在する（How Complex Systems Fail Point 4）。× は要改善 |
| C7 | 根本原因と対策の接続 | 特定された最も深い contributing factor / systemic cause それぞれに、対応するアクションアイテムが少なくとも 1 件ひも付いているか。ひも付いていない systemic cause があれば要改善。**それが唯一の深い原因（＝そこを直さなければ再発する）ならブロッカー** |
| C8 | 対応判断が後知恵で断罪されていない | 診断・緩和の遅れの分析が、対応者がその時点で持っていた情報・メトリクス・アラートの状態を基準に書かれているか。「原因は明らかだったのに見抜けなかった」式の、結果を知ってから見た評価になっていないか（SRE Book: acted on the best information available at the time / Allspaw: why it made sense to do what they did）。× は要改善（ブロッカーにはしない。講評の「タイムライン」欄で指摘） |

**C2 が × → ブロッカー。C1 が到達点（修正可能な機構）に届いていない → ブロッカー。
C7 で唯一の深い原因に対応アクションアイテムがない → ブロッカー。**

### 良い根本原因 / 悪い根本原因（判定を固定するための対比例）

| 論点 | 悪い（proximate 停止 / 単線 / 人間非難） | 良い（systemic / 修正可能な機構を名指し） |
|---|---|---|
| 深さ | 「Elasticsearch のヒープが足りなくなってクラッシュした」 | 「ヒープ上限が固定値で、インデックス増加に対する監視・自動調整・容量レビューのいずれもなく、6 ヶ月かけて閾値へ近づいた」 |
| 単線 vs 複数 factor | 「デプロイ #1183 が接続を張りすぎた」（1 本の連鎖） | 「(a) ステージングが低トラフィックで枯渇が顕在化しない (b) カナリアなしで一括展開 (c) 接続方式を検査するレビュー観点がない —— の 3 つが揃って初めて顕在化した」 |
| システムに触れているが実は人間非難 | 「Why5: チームにテストを書く文化がなかった」 | 「この条件を検証するテストが無く、省略してもゲート（CI）で止まらない」 |
| レビューを原因にしている | 「Why4: レビューで接続方式の問題を見落とした」 | 「接続数・プール使用率を検証するテストが CI に無く、この変更クラスがゲートを通過した」（コードレビューは欠陥検出の手段ではない —— qa-process.md 参照） |
| counterfactual を原因に置く | 「監視を入れておけば防げた（＝これが根本原因）」 | 「新規の外部依存に監視を要求するチェックがなく、監視対象の決定が実装者の裁量に委ねられていた」 |
| why now の欠落 | 「設定不整合で停止した」（いつからか不明） | 「キュー名は 3 週間前から 2 箇所に分かれていたが、この日まで両者を変更する作業がなく顕在化しなかった」 |

要改善に留める境界例: 「Why3: 監視の対象外だった」で止まる（"システム" に触れては
いるが、なぜ対象外だったのか —— 監視追加のプロセスが無い / 判断が実装者裁量 —— に
達していない → proximate 寄り、C2 と重複判定）。
「レビューで気づけなかった」を根本原因に置いているものは、それ自体を要改善とする
（コードレビューは欠陥検出の手段ではなく、TDD の前提ではその不具合を捕らえるテストが
存在すべきだった —— qa-process.md「コードレビューをすり抜け工程の原因にしない」）。

該当なしの例: 種別がバグで 5 Whys / 根本原因欄が本文に存在しない。

（回帰テストの有無は Step 3 / qa-process.md §4 で評価する。ここでは扱わない。）

## D. 影響評価

| # | 次元 | 合格の目安 |
|---|---|---|
| D1 | customer（顧客） | 影響ユーザー数・影響機能。定量値がある。SLO 逸脱幅・エラーバジェット消費への言及があれば加点（Google SRE） |
| D2 | data（データ） | データ損失 / 不整合の有無と範囲 |
| D3 | financial（金銭） | 逸失売上 / SLA クレジット等（該当すれば）。**値が「試算中 / 財務が確認中」なら定量プロセスが動いている証拠で合格圏**。空欄かつプロセスへの言及もない場合のみ要改善 |
| D4 | reputational（レピュテーション） | 公開ステータスページ・問い合わせ増の有無 |
| D5 | operational（運用） | 対応工数・オンコール負荷 |
| D6 | regulatory（規制 / コンプラ） | 報告義務のある事象か（該当すれば） |

該当しない次元は「該当なし」で可。**D1 に定量値が無い（「多くのユーザー」等）→ 要改善。**

## E. 検知・対応の遅延要因

| # | 項目 | 合格の目安 |
|---|---|---|
| E1 | 検知が遅れた理由 | TTD が長い場合、なぜ気づけなかったかが分析されている |
| E2 | 対応が遅れた理由 | TTR が長い場合、診断・緩和のどこで時間を要したかが分析されている。**かつその分析が後知恵に陥らず、対応者がその時点で入手可能だった情報を前提に書かれている**（C8 と対。「原因は明らかだったのに」式でない） |
| E3 | エスカレーションの適否 | 適切な人へ適切な速さで伝わったか |

（QA/QC 観点の「検知経路」は Step 3 / qa-process.md で扱う。ここは時間の内訳。）
