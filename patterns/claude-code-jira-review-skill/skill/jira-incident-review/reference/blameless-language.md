# 非難的表現の検出と言い換え

Step 5 で使う。人ではなくシステム / プロセスに焦点を当てるための言い換え。

出典: Atlassian（How to run a blameless postmortem）、
incident.io（"Engineer deployed buggy code" → "CI/CD pipeline missed the bug"）、
PagerDuty Postmortem Documentation（The Blameless Postmortem）、
John Allspaw「Blameless PostMortems and a Just Culture」（second story）、
Fred Hebert「Superficial Blamelessness」、
Google SRE Book「Postmortem Culture」。

## 目次

- なぜ言い換えるか
- 検出パターン（日本語 / 英語）
- 言い換えテンプレート
- second story チェック（言い換えで終わっていないか）
- 許容される表現（非難ではない。言い換えを提案しない）
- 報告の書き方（実名は伏せる）

## なぜ言い換えるか

「エンジニアがバグ入りコードをデプロイした」→ 生まれる対策は「再教育」「次から注意」。
これは実効性が無く、再発する。

「CI がそのバグを検出できなかった」→ 生まれる対策は「CI にテストケースを追加」。
これは修正可能なシステム変更で、再発を防ぐ。

同じ事実を、**修正できる対象**を主語にして書き直す。

## 検出パターン

本文（特に根本原因・アクションアイテム）に次があれば非難的表現として拾う。

### 日本語

- 人名 / 役割名 + 「〜し忘れた」「〜を忘れていた」「〜を怠った」
- 「〜すべきだった」「〜しておけばよかった」（= counterfactual かつ非難）
- 「〜のミス」「〜の見落とし」「〜の不注意」「〜の確認不足」「〜の考慮漏れ」
- 「担当者が」「作業者が」で始まり過失を述べる文
- 「オペミス」「ヒューマンエラー」で片付けている

### 英語

- `<name> forgot to` / `failed to` / `should have` / `didn't check`
- `human error` / `operator error` を原因として置いている
- `<name> was responsible for` （過失の含意）

## 言い換えテンプレート

| 非難的 | システム主語への言い換え |
|---|---|
| 「X が手順 Y を実行し忘れた」 | 「手順 Y が手動で、実行を強制する仕組み（CI チェック / チェックリスト / 自動化）が無かった」 |
| 「X が設定値を間違えた」 | 「設定値に対するバリデーションが無く、誤った値がそのまま適用された」 |
| 「レビュアーが見落とした」 | 「この条件を検証するテスト / 静的解析が無く、欠陥がゲート（CI）を通過した」（コードレビューは欠陥検出の手段ではない。qa-process.md 参照） |
| 「X がデプロイ前に確認しなかった」 | 「デプロイ前の確認が任意で、未確認のままデプロイできる経路が存在した」 |
| 「担当者の考慮漏れ」 | 「この条件を扱う要件が明文化されておらず、実装・レビュー・テストのいずれでも検討されなかった」 |
| 「オペミスによる誤削除」 | 「破壊的操作に確認ステップ / ドライラン / 取り消し猶予が無かった」 |

## second story チェック（言い換えで終わっていないか）

出典: Hebert「Superficial Blamelessness」、Allspaw の second story
（「なぜその人がそうするのが理にかなっていたか」を問う）。

**主語をシステムへ言い換えただけでは blameless ではない。** 言い換え後の文が
「〜する仕組みが無かった」で止まっていて、その先に **なぜその仕組みがそうなって
いたか** —— 要件が明文化されていない / コスト判断で省いた / レビュー負荷が高かった /
過去に問題化していなかった / リリース期日のプレッシャー —— が無ければ、それは
表面的な言い換え（superficial blamelessness）である。

判定:
- 非難的表現をシステム主語へ言い換えた各箇所について、対応する根本原因 / 寄与要因が
  「その条件を生んだ組織的・技術的な仕組み」まで踏み込んでいるか確認する。
- 踏み込んでいなければ、blameless 指摘としてではなく **incident-checklist.md C2
  （proximate cause で止まっていない）の観点で「要改善」** とする。
- 例: 「CI がバグを検出できなかった。対策: CI にテスト追加」だけ → 文言は完璧に
  システム主語だが、「なぜそのテストが無かったのか」が無い → C2 で要改善。

## 許容される表現（非難ではない。言い換えを提案しない）

- **役割・システムを主語にした事実記述**: 「デプロイパイプラインがロールバックを
  自動実行しなかった」
- **実名でのタイムライン記録**: 「HH:MM &lt;実名&gt; が &lt;操作&gt; を実行 / 開始 /
  確認した」は、過失を述べる動詞（〜し忘れた、〜を怠った、〜すべきだった、〜のミス）
  を伴わない限り、そのまま許容する。言い換えを提案しない。
- **対応者・指揮者の実名記載それ自体**: 非難ではない。指摘するのは、記名が「誰が
  悪いか」の文脈（「〜は X の責任だった」「X の判断ミス」）に置かれている場合のみ。
- **「時間を要した / 遅れた」という記述**: 原因を人の資質に帰していない限り
  （「X がのんびりしていた」ではなく「メトリクスが正常値で切り分けに 20 分を要した」）
  許容する。
- **意思決定の記述**（後知恵の断罪でなく、その時点の情報で）:
  「その時点ではメトリクスが正常値で、原因の切り分けにさらに 20 分を要した」

## 報告の書き方

各検出箇所について次の 2 つを出す。**実名は伏せる**（引用は非難的表現の型が
わかる最小限にとどめる。引用が必要なのは precision のためであって、実名を含める
必要はない）。

- 該当箇所: 「&lt;担当者&gt; がステージング検証を実行し忘れた」（実名は伏せる）
- 言い換え案: 「ステージング検証が手動で、未実施のまま本番マイグレーションを実行
  できる経路が存在した」

該当ゼロなら「非難的表現は検出されませんでした」と明記する。
推測で「これは暗に人を責めている」とまでは踏み込まない（引用できる表現に限る）。

このレビューの出力は**プロセス改善のためのもので、担当者の人事評価に転用しては
ならない**（SKILL.md 冒頭の免責を参照）。
