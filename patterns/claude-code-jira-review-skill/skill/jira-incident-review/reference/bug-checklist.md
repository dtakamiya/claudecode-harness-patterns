# 開発時の障害 / バグチケット チェックリスト

Step 2 で使う。インシデントより軽量な基準。各項目に `合格 / 要改善 / 該当なし` を付ける。
情報が本文になく判定できない項目は「要改善（記載なし）」とする。
「記載なし」は原則として軽微指摘だが、**SKILL.md「ブロッカーの基準」に挙げた項目に
該当するものはブロッカーに昇格する**。

出典: Bug triage 各種（Plane, BugReel, Bird Eats Bug, Supportbench）、
「How to Write a Bug Report That Actually Gets Fixed」、
incident.io（"CI missed the bug" 型の再構成）。

---

## A. 記述の質

| # | 項目 | 合格の目安 |
|---|---|---|
| A1 | タイトル | 症状が一文で分かる。「バグ」「動かない」だけは不可 |
| A2 | 再現手順 | 番号付きで、第三者がなぞって再現できる粒度。前提状態も書かれている |
| A3 | 期待結果 vs 実際結果 | 両方が明記され、差分が明確 |
| A4 | 証跡 | ログ / スクリーンショット / スタックトレース / エラーメッセージのいずれか |
| A5 | 環境情報 | OS・アプリ/ライブラリのバージョン・ブラウザ・データ条件など再現に必要なもの |

**A2 が無い / 「時々落ちる」等で再現不能 → ブロッカー**（修正の起点が無い）。

## B. トリアージ

| # | 項目 | 合格の目安 |
|---|---|---|
| B1 | severity と priority が区別されている | severity=システムへの影響度、priority=対応の急ぎ度。混同していない |
| B2 | 再現可否が確認済み | 「再現した / できなかった / 環境依存」のいずれかが記録されている |
| B3 | 担当アサイン | 対応者が決まっている（未アサインで放置されていない） |
| B4 | 関連リンク | 原因と疑われる PR / コミット / 関連チケットへのリンク（判明していれば） |

## C. 原因と修正

| # | 項目 | 合格の目安 |
|---|---|---|
| C1a | 作り込みの技術的原因 | 何が原因だったかが（修正後なら）書かれている。「直した」だけで終わっていない |
| C1b | すり抜けの構造的理由 | なぜその変更がユニットテスト・結合テスト・型検査・lint のいずれも通過できたか、その構造的な理由が特定されている。「該当チェックがなかった / あったが不十分だった / コスト判断で省いた」のいずれかに踏み込んでいるか（proximate な「PR で行が消えた」「レビューで見落とした」で止まっていないか。**コードレビューはすり抜け工程に含めない** —— qa-process.md の注記参照） |
| C2 | 修正内容 | どう直したかが分かる（PR リンクで可） |
| C3 | 非難的表現が無い | C1a / C1b の本文に人名 + 過失動詞が無い（Step 5 で扱う） |

**C1b が「PR で行が消えた」等の proximate な記述で止まっている → 要改善。**

## D. QA/QC

**D 節は Step 3（qa-process.md）と内容が重複する。Step 2 では簡易確認に留め、
詳細判定と合否は Step 3 / qa-process.md で行う**（incident-checklist.md の E 節と同じ扱い）。

| # | 項目 | 簡易確認 |
|---|---|---|
| D1 | 作り込み工程 | いつ / どの変更で入ったかに言及がある |
| D2 | すり抜け工程 | 各テストのレイヤ（unit / integration / E2E / 型 / lint）について「該当チェックがなかった / あったが不十分 / コスト判断で省いた」のいずれかが特定されている（「言及がある」だけでは不足。コードレビューは含めない。詳細は qa-process.md §2） |
| D3 | 回帰テスト | この不具合を再発させないテストが追加された / 追加チケットがある |

**開発時のバグでも D2・D3 が空 → 要改善**（同じクラスのバグが再発する）。
リリース済み機能で顧客影響が出たものは、バグでなくインシデント側の基準で見る
（種別判定は SKILL.md Step 1）。
