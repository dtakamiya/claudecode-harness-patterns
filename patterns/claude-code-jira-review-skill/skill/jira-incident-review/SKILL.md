# Jira Incident Review

貼り付けられた Jira チケット（本番インシデント / 開発時の障害）をレビューする。
**チェックリスト全項目に合否を付ける網羅方針**。記述の質だけでなく、
そのチケットが露呈させている**品質プロセスの穴**（検知・テスト・再発防止）を重く見る。

このスキルはチケットを編集しない。修正はレビュー結果を受けて人が行う。

**このスキルが検査するのは「根本原因の記述が深掘りの構造を備えているか」まで。**
根本原因が事実として正しいか、対策が技術的に有効かは、コード・メトリクス・設計の
確認が必要でスコープ外。それらは「要確認」として PIR 会議の議題に回す。

## 目次

想定利用者 → 入力 → 進行チェックリスト → Step 1〜6（種別判定 / 種別別チェックリスト /
QA/QC 観点 / アクションアイテム評価 / blameless スキャン / 報告）

## 想定利用者

チケット作成者 / 対応チーム自身のセルフチェック、または PIR ファシリテータの会議準備を
想定する。**出力は改善提案であり、管理者が担当者の評価に使うこと、他者が「これを
埋めろ」と督促に使うことは想定しない**（Google SRE Book "Postmortem Culture":
ポストモーテムを書くことは報われるべきで、罰せられるべきではない）。

## 入力

チケット本文（説明・コメント・フィールド）を貼り付けてもらう。
Jira への接続はしない。**URL だけ渡された場合は本文の貼り付けを依頼して停止する。**
本文が断片的（コメント欄が切れている等）なら、その旨を報告に明記する。

## 進行チェックリスト

以下を応答へコピーし、完了ごとに埋めながら進める。

```text
Review Progress:
- [ ] Step 1: チケット種別を判定する（インシデント / バグ）
- [ ] Step 2: 種別のチェックリストを読み、全項目に合否を付ける
- [ ] Step 3: QA/QC 観点を評価する（検知経路・すり抜け工程・再発防止の実効性・回帰テスト・副作用）
- [ ] Step 4: アクションアイテムを 7 軸+カバレッジで個別評価する
- [ ] Step 5: 非難的表現をスキャンし、言い換え案を作る（言い換え先が分析で掘られているかも見る）
- [ ] Step 6: false-positives.md と照合し、総評（ブロッカー→軽微）と追記文案を書く
```

## Step 1: 種別判定

| 手がかり | 種別 |
|---|---|
| 本番稼働中の障害、顧客影響、SEV/P1 表記、オンコール招集、ダウンタイム | インシデント |
| 開発中・未リリース、再現手順が本文の主内容、QA 検出、機能ブランチの不具合 | バグ |

**曖昧なら両方の視点で講評する**（無理にどちらかへ寄せない）。判定の根拠を一文で述べる。
**Step 2 で「該当なし」が半分を超えたら種別判定を再考する**（誤判定のサイン）。

## Step 2: 種別別チェックリスト

種別に応じて**片方だけ**読み、記載された全項目に `合格 / 要改善 / 該当なし` を付ける。
※種別を曖昧と判定した場合のみ両方読む。

| 種別 | 参照 |
|---|---|
| インシデント | [reference/incident-checklist.md](reference/incident-checklist.md) |
| バグ | [reference/bug-checklist.md](reference/bug-checklist.md) |

参照ファイルは**このステップに来たときに読む**。先読みしない。

## Step 3: QA/QC 観点（重点）

[reference/qa-process.md](reference/qa-process.md) を読み、次の軸で評価する。

- **障害分類**: 実装バグ / 設計欠陥 / キャパシティ / 外部依存 / 組織・プロセス。
  以降の問いを分類に応じて使い分ける
- **検知経路**: 監視・アラートで検知したか、顧客/他者報告で検知したか（後者は監視の穴）
- **すり抜け工程**（実装バグのみ）: どの**テストのレイヤ**（unit / integration / E2E /
  型 / lint / staging / canary）をすり抜けたか。**コードレビューは含めない**
- **再発防止の実効性**: 品質プロセスへの**恒久的な組み込み**か、「注意・周知・再教育・
  手順書に一文」で終わっていないか。**最深の systemic cause に対策が対応しているか**
- **回帰テスト**: 修正に対する回帰テストが定義されているか
- **副作用**: 恒久策が新たな失敗点・運用負荷を増やさないか、許容する判断があるか

**プロセスの穴を重く**見る。記述が整っていても、すり抜けたテストのレイヤが未特定・
対策が「周知」止まり・最深層に対策が紐付かないならブロッカー。

## Step 4: アクションアイテム評価

[reference/action-items.md](reference/action-items.md) を読み、チケット内の各アクション
アイテムを 7 軸（Specific / Owned / Due-dated / 分類 / 検証 / 追跡 / クラス有効性）で
個別評価する。**本文に該当箇所が引用できるものだけを不備として指摘する。**
併せて**カバレッジ**（各 contributing factor に対応アクションアイテムがあるか）を
突き合わせる。個数・詳細は reference。

## Step 5: blameless スキャン

[reference/blameless-language.md](reference/blameless-language.md) を読み、非難的表現
（人名 + 過失動詞、「〜し忘れた」「〜すべきだった」「〜のミス」等）を洗い出す。
該当する各箇所に**引用（実名は伏せる）**と**システム主語への言い換え案**を出す。
言い換え先が根本原因分析で掘り下げられているか（second story）も確認し、proximate 止まり
なら blameless 指摘でなく C2 の指摘に回す。該当ゼロならゼロと明記する。

## Step 6: 報告

報告を書く前に [reference/false-positives.md](reference/false-positives.md) と照合し、
該当する「要改善」「ブロッカー」候補を棄却または降格する。

### 判定値の対応表

| 使う場面 | 値 | 補足 |
|---|---|---|
| 必須項目チェック表 | `合格 / 要改善 / 該当なし` | 3 値 |
| 「要改善」の内訳 | `要改善（記載追加で解消）` / `要改善（内容の見直しが必要）` | 前者は情報の欠落、後者は分析・対策の質 |
| 「記載なし」の扱い | 原則「要改善（記載追加で解消・軽微）」 | ただし下の「ブロッカーの基準」に該当する「記載なし / 未特定」は**ブロッカーに昇格** |
| アクションアイテム表の各軸 | `○ / ×` | 簡易記号。3 値とは別体系 |
| アクションアイテム表の総合 | `合格 / 要改善 / ブロッカー` | この 3 値だけが必須項目チェックと揃う |

### ブロッカーの基準

**条件の正典は各 reference の該当項目（太字「→ ブロッカー」）。** ここはその索引で、
文言は持たない。Step 2〜4 で読んだ reference の太字条件に該当したものを数える。

| 群 | 定めるファイルと項目 |
|---|---|
| インシデント（記述） | `incident-checklist.md` A（必須フィールド 4 点）、C（C1 到達点未達 / C2 × / C7 唯一の深い原因が未対応） |
| バグ（記述） | `bug-checklist.md` A2（再現手順 / 再現性） |
| QA/QC（種別共通） | `qa-process.md` §0 判定の指針（分類別の問い）、§1（顧客報告検知でアラートなし）、§2（すり抜け工程未特定）、§3（周知止まり）、§4（回帰テストなし＝インシデント）、§5（過去の同一障害の未検証） |
| アクションアイテム | `action-items.md` 出力表（Owned / Due が ×）、個数の目安（ゼロ件）、カバレッジ（最深 factor が未対応） |
| 種別共通 | `blameless-language.md`（非難的表現が根本原因欄・アクションアイテム欄にある） |

reference に太字条件が無いものはブロッカーにしない。それ以外の「要改善」は軽微指摘。

### 出力形式

```markdown
## チケットレビュー結果

> このレビューはチケットの記述と品質プロセスの穴についての**改善提案**です。特定の
> 担当者・対応者の評価・査定・責任追及の材料として使うことを意図していません。
> 「ブロッカー」はクローズ前に埋めるべき情報の欠落であり、個人の失点ではありません
> （Google SRE Book "Postmortem Culture" / Allspaw "Just Culture"）。

**種別**: インシデント / バグ / 判定曖昧（<根拠一文>）
**全体評価**: <2〜3 文>
**ブロッカー**: N 件

### 良い点

- <合格項目のうち特筆すべきもの 2〜3 個。無ければ「特記なし」>

### 必須項目チェック

| 項目 | 判定 | 根拠 |
|---|---|---|
| <各項目> | 合格 / 要改善（記載追加で解消 / 内容の見直し） / 該当なし | <本文の該当箇所、または「記載なし」> |

同一判定が連続する項目はグループ化して 1 行にまとめてよい。

### 講評

- **タイムライン**: <検知/復旧までの時間、フェーズの欠落、後知恵での断罪の有無>
- **根本原因**: <因果の深さ（到達点）、単一 root cause、why now、counterfactual、
  最深層とアクションアイテムの接続>
- **影響評価**: <6 次元のカバー、定量値、SLO 影響>

### QA/QC 講評（重点）

- **障害の分類**: <実装バグ / 設計欠陥 / キャパシティ / 外部依存 / 組織>
- **検知経路**: <監視 / 報告。監視の穴>
- **すり抜け工程**: <実装バグならテストのレイヤが特定されているか、レビューを原因に
  していないか。実装バグ以外なら分類別の問いへの答え>
- **再発防止の実効性**: <恒久的なプロセス組み込みか、「周知」止まりか、最深層に対応か>
- **回帰テスト**: <定義されているか>
- **副作用**: <新たな失敗点・運用負荷を増やさないか、許容判断があるか>

### アクションアイテム評価

| 項目 | Specific | Owned | Due | 分類 | 検証 | 追跡 | クラス有効性 | 総合 |
|---|---|---|---|---|---|---|---|---|
| <各アクションアイテムの引用> | ○/× | ○/× | ○/× | ○/× | ○/× | ○/× | ○/× | 合格 / 要改善 / ブロッカー |

**カバレッジ**: <contributing factor と対応アクションアイテムの突き合わせ。空欄の
factor、最深 factor の放置>

### blameless 指摘

- 該当箇所: 「<引用（実名は伏せる）>」 → 言い換え案: 「<システム主語の表現>」
  （言い換え先: <分析で掘られている / proximate 止まりで C2 の要改善>）
- （該当なしなら「非難的表現は検出されませんでした」）

### 追記推奨文案

（作成者の自己追記用の下書きです。本文に既にある項目は含めず、欠落項目のみ。
命令形を避け「〜を追記すると PIR で議論しやすくなります」の口調。）

<欠落項目の穴埋めテンプレート>
```

**ブロッカーがゼロならゼロと明示する。** 埋まっている項目に無理な難癖を付けない。
「要改善」は記載の欠落・曖昧さに限り、内容が妥当なら「合格」とする。このスキルは
1 枚のチケット本文だけを見る。関連チケット・コード・監視ダッシュボードの確認が要る
指摘は「要確認」と添え、ブロッカーにしない。
