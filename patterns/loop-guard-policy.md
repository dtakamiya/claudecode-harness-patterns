# Loop Guard Policy

## 1. 目的と適用範囲

本ポリシーは、Claude Codeを定期的・反復的に起動するループ（cron、launchd、デスクトップアプリやクラウドの定期タスク、`/loop`など）の共通規則である。次の2点を定める。

1. **成功は検証で判定する**: プロセスが正常終了したことではなく、決定論的な検証を通ったことを成功とする。
2. **止まる条件と予算を持つ**: 仕事が無ければ起動せず、上限に達したら止まり、失敗が続けば自動で休止する。

適用対象は、人間が毎回の結果を見ない無人ループすべてである。開発サイクル（バックログから1項目を実装する）、定期レポート、監視ジョブを含む。人間承認の扱いは[Human Gate Policy](human-gate-policy.md)を正本とし、本ポリシーはそれを変更しない。

対象外: バックログ項目の受け渡し形式は[Loop State Handoff](loop-state-handoff.md)で定める。子セッション完了のイベント駆動化は、本ポリシーの実行記録を前提に別途定める。

## 2. 観測した問題

ある個人環境の定期実行基盤（Claude Codeを起動するcronジョブ25本、うち有効15本）の実行記録1,204件を2026-11-15に集計した。

| 観測 | 値 | 意味 |
|---|---|---|
| `status: success` | 1,202件（99.8%） | 記録上はほぼ全件が成功 |
| 1時間を超えて`success` | 85件 | 同じ8日間に集中している。このうち52件は約6時間で終わっており、実行基盤側の上限で打ち切られたとみられる |
| 60秒未満で終了 | 764件（63%） | 有用な仕事をしたのか、何もせず終わったのかを記録から区別できない |
| 結果の要約 | 記録なし | 記録の項目は時刻・セッションID・status・所要時間・errorだけで、成果物も検証結果もない |
| レート制限の選択画面 | 自動実行のセッションで98回 | ループが利用枠を使い切り、制限画面で止まっている兆候 |

ここから次の2つが分かる。

- **statusが成否を表していない。** 6時間の停滞も、何もしなかった実行も`success`として記録されている。成功率99.8%は品質の指標にならない。
- **止まる仕組みが無い。** 仕事の有無にかかわらず毎回モデルを起動し、停滞しても次の起動が重なり、利用枠を使い切っても止まらない。

長時間の停滞がなぜ起きたか（レート制限待ちか、承認待ちか、外部APIか）は記録から特定できない。特定できないこと自体が、本ポリシーで実行記録を定める理由である。

## 3. 成功は検証で判定する

### 3.1 結果の分類

1回の実行結果を次のいずれかに分類する。単一の`success`は使わない。

| 結果 | 条件 | 次回の扱い |
|---|---|---|
| `VERIFIED` | 検証をすべて通った | 通常どおり |
| `NOOP` | 事前ゲートで仕事が無いと判定し、モデルを起動しなかった | 間隔を延ばす候補（4.4） |
| `FAILED` | 検証に落ちた、または出力がschemaに合わない | 同じ項目を1回だけ再試行（3.3） |
| `TIMED_OUT` | 実行時間の上限に達した | 失敗として数える |
| `BUDGET_EXCEEDED` | 回数・費用の上限に達した | その日は止める |
| `RATE_LIMITED` | レート制限を検知した | 待たずに終了し、次の起動に任せる |
| `BLOCKED` | 再試行しても失敗した、または人間の判断が必要 | 項目を保留にして通知する |

### 3.2 検証はスクリプトが行う

- 検証はモデルの外で、スクリプトが終了コードとファイルで判定する。AIの自己申告（「完了しました」「テストは通りました」）は検証として扱わない。
- ループの種類ごとに、検証の中身を事前に決めておく。

| ループの種類 | 検証の例 |
|---|---|
| 開発サイクル | test・typecheck・lintの終了コードが0、差分が対象パスの中だけ、差分が空でない |
| レポート・要約 | 出力ファイルが今回の実行で作られた、必須の見出しがある、空でない、日付が今日 |
| 監視 | 判定結果がschemaに合う、異常ありの場合は通知が送られた |

- モデルの出力は`claude -p --output-format json --json-schema`で構造化し、スクリプトは`structured_output`フィールドがあることを確認してから使う。無ければ`FAILED`とする。
- 検証に使ったcommand、終了コード、確認したファイルを実行記録に残す（5章）。

### 3.3 再試行は1回まで

- `FAILED`になった項目は、失敗した検証の出力を添えて1回だけ再試行する。
- 再試行でも失敗したら`BLOCKED`にして通知する。同じ項目を次の起動で自動的に再開しない。人間が保留を解除するまで、その項目は選ばれない。
- 再試行のたびにモデルやeffortを上げる場合は、上げた事実を記録する。上げても通らないものを上げ続けない。

## 4. 止まる条件と予算

### 4.1 事前ゲート（モデルを起動する前）

スクリプトが次を確認し、1つでも当てはまればモデルを起動せずに終了する。

- kill switch（停止用のファイルや設定値）がある → 終了
- 前回の実行がまだ動いている（lockがある） → 終了。起動を重ねない
- 処理対象が無い（バックログが空、前回から入力が変わっていない） → `NOOP`
- その日・その月の予算を使い切っている → `BUDGET_EXCEEDED`
- 自動休止中（4.5） → 終了

入力が変わったかどうかは、入力ファイルやチケット一覧のハッシュを前回と比べて判定する。この判定にモデルを使わない。

### 4.2 1回あたりの上限

| 上限 | 設定 | 備考 |
|---|---|---|
| ターン数 | `claude -p --max-turns` | ループの種類ごとに決める |
| 費用 | `claude -p --max-budget-usd` | 推定値で超えることがあるため、日次予算に余裕を残す |
| 実行時間 | スクリプト側のtimeout | 直近の実行時間のp95の2倍程度を目安にする。実行基盤の既定値（例: 6時間）に任せない |

timeoutで止めたら`TIMED_OUT`として記録する。正常終了と同じ扱いにしない。

### 4.3 日次・月次の予算

- `--output-format json`の`total_cost_usd`を実行ごとに台帳へ足し込む。
- 台帳はジョブ単位と全体の両方で持つ。全体の上限は、手動で使う分を残した値にする。
- 上限に達したら事前ゲートで止める。実行中のプロセスは4.2の上限で止める。

### 4.4 仕事が無いときは間隔を延ばす

- `NOOP`が3回続いたら、次の起動間隔を2倍にする。上限は元の間隔の8倍とする。
- `VERIFIED`が出たら元の間隔に戻す。
- cronの定義そのものは書き換えず、事前ゲートで「前回から何分たったか」を見て判定する。

### 4.5 失敗が続いたら自動で休止する

- `FAILED`・`TIMED_OUT`・`RATE_LIMITED`が合わせて3回続いたら、そのジョブを自動で休止し、通知する。
- 休止の解除は人間が行う。解除の際に原因を実行記録へ書く。
- `RATE_LIMITED`では、プロセスの中で制限の解除を待たない。待つと停滞が`success`に化け、後続の起動とも重なる。

## 5. 実行記録

実行ごとに1行を追記する。上書きしない。

```yaml
run_id: 2026-11-15T09:17:01Z-dev-cycle
job: dev-cycle
outcome: VERIFIED            # 3.1の分類
gate: {reason: null}         # 事前ゲートで止めた場合はその理由
item: backlog/042            # 処理した項目。NOOPならnull
attempt: 1                   # 再試行なら2
model: claude-sonnet-5-5
effort: medium
duration_ms: 184000
turns: 17
cost_usd: 0.42
verification:
  - {cmd: "npm test", exit: 0}
  - {cmd: "npm run typecheck", exit: 0}
  - {check: "diff_in_scope", ok: true}
artifacts: [reports/2026-11-15.md]
next_interval_min: 60        # 4.4の結果
```

- `outcome`と`verification`は必須とする。`verification`が空の`VERIFIED`は記録しない。
- 本文や秘密情報は記録しない。成果物はパスかURLで参照する。

## 6. 指標

週次で次を見る。

| 指標 | 見る理由 |
|---|---|
| `VERIFIED`率 | ループが実際に役立っているか |
| `NOOP`率 | 起動間隔が細かすぎないか |
| `VERIFIED` 1件あたりの費用 | 費用対効果 |
| `TIMED_OUT`・`RATE_LIMITED`の件数 | 上限と予算が合っているか |
| `BLOCKED`の滞留数 | 人間の確認が追いついているか |

`VERIFIED`率が低いジョブは、検証が厳しすぎるのではなく、ジョブの粒度か入力に問題があると考えて見直す。

## 7. 段階導入

1. **記録だけ**: 既存のジョブを変えず、5章の形式で記録し始める。`outcome`は終了コードとtimeoutだけで決める。
2. **検証の追加**: 実行回数の多いジョブから、3.2の検証を入れて`VERIFIED`と`FAILED`を分ける。
3. **上限の追加**: 4.1の事前ゲートと4.2の上限を入れる。timeoutは段階1の記録から決める。
4. **自動調整**: 4.4の間隔延長と4.5の自動休止を有効にする。

各段階は1〜2週間記録を取り、6章の指標を見てから次へ進む。
