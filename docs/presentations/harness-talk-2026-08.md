# 社内発表 構成案＋台本 — 「ハーネス」でAI駆動開発をチームの仕組みにする

- **想定時間**: 10分（本編 約9分＋予備1分）
- **想定聴衆**: 社内エンジニア。Claude Code を触ったことはあるが、ハーネスという言葉は初耳という層。
- **ゴール**: 「AI駆動開発を続けるにはハーネスが要る」を共通言語にし、チームの配布物を使ってもらう入口を作る。
- **構成の考え方**: AI駆動開発の定義 → 検証税 → 実践で出る壁 → **壁の根っこは「出力がブレる」こと／ハーネスは不確実性を小さくする装置** → **ハーネスの定義（コンテキスト・スキル・エージェント）** → チームでの共有。スライド4と5が背骨。

## スライド1: AI駆動開発とは — 補助ツールと中核の違い

**スライドに載せる要点**
- 人が「**何をつくるか**」を決め、AIが「**どうつくるか**」を担う
- AIを補助ツールではなく開発プロセスの**中核**に置く＝**起点と終点が入れ替わる**

| | 補助ツールとして使う | 中核に置く |
|---|---|---|
| **起点** | 人が書き始める | **AIに委譲する** |
| 作業の単位 | 行・ブロック | **タスク・機能まるごと** |
| 人の動き | 書く（AIが手伝う） | **意図を決め、検証する** |
| 人が見るもの | 自分が書いたコード | **AIが書いた大量の差分** |
| AIを外すと | 遅くなるだけ | **プロセスが成立しない** |

- 境目の判定: **AIの出力を、人がその場で判断しきれているか**
- 2025年のバイブコーディング → 2026年は**仕様駆動（Spec-Driven）**へ
  - 正本が「実装されたコード」から「**人の意図＝仕様**」に移った
- 変わらないもの: 意思決定、人間の承認、検証の規律

**台本**
> まずAI駆動開発の定義から。開発の全工程に生成AIを組み込んで、人が方針と品質を統御しながらAIに実装を任せる進め方です。人が「何をつくるか」を決め、AIが「どうつくるか」を担います。
>
> よく「補助ツールではなく中核に置く」と言われますが、それが何を指すのかを表にしました。違いは**起点と終点が入れ替わること**です。
>
> 補助ツールなら起点は人です。自分で書き始めて、詰まったらAIに聞き、提案を採用するか却下する。AIは加速装置なので、外しても遅くなるだけです。中核に置くと逆転して、起点がAIになり人は終点に回ります。タスクを丸ごと委譲して、返ってきたものを検証する。外すとプロセスが成立しません。
>
> 見分け方は、AIの出力を人がその場で判断しきれているかどうか。補完の候補を1つ選ぶ程度なら判断できています。でも機能まるごとの差分が返ってきて、その場で妥当性を判断しきれない量になったら、もう中核に置いている状態です。
>
> なお2026年の潮流として、雰囲気で指示するバイブコーディングから、仕様を先に固める仕様駆動へ移っています。人が書かなくなったからこそ、意図を書き残すことが重要になった、という流れですね。
>
> 一方で変わらないものもあります。何を作るかの意思決定、外部に影響する操作への人間の承認、テストと検証の規律。むしろ重要度は上がります。AIのレビューが人間の承認を代替することはありません。

**補足（質疑用）**
- 仕様駆動開発（SDD）のツール例: GitHub Spec Kit、AWS Kiro、Claude Code。主要ベンダーが揃って「仕様を先に書く」方向を打ち出したのが2026年の特徴。
- うちのハーネスでは PHASE-1〜2 の要件定義・要件レビューがこれに当たる。受入基準は EARS 構文で検証可能な形に落としている。
- 補助的な利用との境目は「AIの提案を人がその場で判断しきれるか」。判断が追いつかない量が出てきた時点でAI駆動開発に入っている。
- **この表が次スライドへの伏線**: 「人が見るもの」が自分のコードからAIの大量の差分に変わる → だから検証税が発生する。中核に置くから税がかかる、補助的に使う分にはかからない。

## スライド2: 検証税 — AIを入れると必ず課税される

**スライドに載せる要点**
- 人が見る量が「自分が書いた分」から「**AIが書いた大量の差分**」へ跳ね上がる
- → 検証コストが新たに発生。律速は**書く速度から検証する速度へ**
- DORA の報告する方向性:
  - **スループットは上がる**
  - 一方で **デリバリの安定性は下がる**
- この増えた検証コスト＝ **verification tax（検証税）**
- **AIを入れると必ず課税される。問題はこの税を誰が払うか**

**台本**
> 人が書かなくなると、代わりに人が見る量が跳ね上がります。自分が書いた分だけを見ればよかったのが、AIが書いた大量の差分を見ることになる。律速が、書く速度から検証する速度へ移るわけです。
>
> DORAの調査が方向性を示しています。AIを入れるとスループットは上がる。ところが同時に、デリバリの安定性のほうは下がる傾向がある。コードが速く大量に出てくる分、レビューと検証が追いつかなくなるからです。
>
> この増えた検証コストを、私は「検証税」と呼んでいます。AIを入れると必ず課税される。ゼロにはできません。問題は、この税を誰が払うかです。

**補足（質疑用）**
- 出典: DORA "Impact of Generative AI in Software Development"（版 2025.2）。**観察研究における関連であり、個々の変更に対する因果効果ではない**点に注意。数値を問われたら「方向性の報告であって、うちで何%出るかを約束する数字ではない」と答える。
- 「AI は増幅器」という総括が本質: 既存の強みも弱みも拡大される。ツール単体ではなく、それを載せる組織の仕組みのほうが投資効果を決める。⚠️ **この総括を英語原文の引用として出さないこと**（下記は出典未確認のため、口頭では自分の言葉で言う）: *"The greatest returns on AI investment come not from the tools themselves but from a strategic focus on the underlying organizational system."*

## スライド3: 実践するとぶつかる壁

**スライドに載せる要点**
- **Jカーブ**: 導入直後はむしろ生産性が下がる
  - 学習コスト＋検証税＋増えたコード量への対応
- 現場で起きること:
  - 「それらしく完了しました」— 完了が**自己申告**
  - セッションが切れると文脈が消える — 続きから再開できない
  - 人によって使い方がバラバラ — 成果が個人技になる
  - 危ない操作を毎回人が見張るのは続かない
- 新しい2つの負債:
  - **認知的負債** — 動くが、誰も中身を説明できない
  - **意図的負債** — AIは「何を作ったか」は出すが「**なぜそう作ったか**」は残さない

**この4つ＋2つの負債、根っこはひとつ** → 次スライドへ

**台本**
> ここが今日の中心です。実際にやると、だいたい同じところでつまずきます。
>
> まず「Jカーブ」。AIを入れると最初はむしろ生産性が下がります。学習コストと検証税の分です。いわば変革の授業料ですね。谷を知らずに始めると、効果が出る前に諦めることになります。
>
> 具体的には、完了がAIの自己申告になる。セッションが切れると文脈が消える。人によって使い方の差が開く。同じモデルを使っているのにです。
>
> そして新しい2種類の負債。動いているけれど誰も中身を説明できない認知的負債と、「なぜそう作ったか」が残らない意図的負債です。
>
> ここで一度立ち止まります。これら、根っこは同じだと思っています。

**補足（質疑用）**
- Jカーブと検証税: 導入初期は学習コストと検証コストが先に立ち、効果が出るまでに谷がある、という経験則。**ROI や回収期間の具体的な数値は、出典を確認できていないので本番では出さない。** 聞かれたら「うちで計測してベースラインを取るところから」と答える。
- 認知的負債・意図的負債: 2026年の国内議論で整理された概念。原因として「認知的降伏」— AIの出力を過剰に信頼して精査しなくなる心理状態が挙げられる。対策は前者がレビューとウォークスルー、後者が ADR や仕様による意図の明示的記録。
- **うちの対策**: 意図的負債には Change Intent Record（`patterns/change-intent-record.md`）。目的・理由・制約・却下した代替案を短く残す規約で、「会話履歴を設計文書の代用にしない」ことを明文化している。
- 参考（数字を出すなら留保必須）: METR の2025年RCTで、経験豊富なOSS開発者がAI使用時に19%遅くなった一方、本人は20%速くなったと感じたという結果がある。ただし **METR自身が後にセレクションバイアス等の問題を公表**しており、一般化はできない。「体感と実測はズレうる」という論点に留めるのが安全。

## スライド4: なぜハーネスが必要か — 不確実性を小さくする

**スライドに載せる要点**

さっきの壁の根っこは、ひとつ:

> **同じことを頼んでも、同じ結果が返ってこない**

**ブレる要因は4つあり、どれも消せない**

| 要因 | 例 |
|---|---|
| **モデルそのもの** | 同じ指示でも生成のたびに違うものが出る |
| **人（使い方）** | 指示の粒度、渡す文脈、plan modeを使うか |
| **モデル選択** | Sonnet / Opus / Fable で結論が変わる |
| **Effort（徹底度）** | 読むファイル数・テスト実行・やり切る深さが変わる |

- 補助ツールなら、ブレても**その場で人が弾ける**（判断が追いつく量だから）
- 中核に置くと弾けない → **ブレがそのまま成果物の品質差になる**
- 「うまくいくときはいく」＝**運任せ**。チームでは再現できない

**ハーネス＝出力のブレを、結果のブレにしない仕組み**

| 打ち手 | 何を固定するか |
|---|---|
| CLAUDE.md / rules / Skills | **入力**を揃える（人による差を減らす） |
| 工程・成果物・ゲート | **通り道**を固定する（どのモデルでも同じ関門） |
| テスト・静的解析の終了コード | **合否判定**を固定する（Effortに依存しない） |
| 進捗・handoffファイル | **状態**を固定する（セッションに依存しない） |

- モデルは非決定的なまま。**その周りを決定論的に固める**
- 目的は「AIを賢くする」ことではなく、**下振れを切ること**

**台本**
> さっきの壁を並べましたが、根っこはひとつだと思っています。**同じことを頼んでも、同じ結果が返ってこない**。これに尽きます。
>
> ブレる要因は4つ。モデル自体が非決定的で、同じ指示でも毎回違うものが出る。人によって指示の粒度も渡す文脈も違う。SonnetかOpusかで結論が変わる。Effortをどこまで上げるかで、読むファイル数もテストの実行も変わる。どれも消せません。
>
> ここで効いてくるのが、さっきの「補助ツールか中核か」です。補助ツールなら、ブレてもその場で人が弾けます。でも中核に置くと弾けない。ブレがそのまま成果物の品質差になります。「うまくいくときはいく」は運任せということで、チームでは再現できません。
>
> だからハーネスは、**出力のブレを、結果のブレにしない仕組み**だと考えています。ルールとスキルで入力を揃え、工程とゲートで通り道を固定し、合否は終了コードで決めてEffortに依存させず、状態はファイルに置いてセッションに依存させない。
>
> モデルは非決定的なままでいいんです。その周りを決定論的に固める。狙いはAIを賢くすることではなく、**下振れを切ること**です。

**補足（質疑用）**
- **この整理は自分の設計思想そのもの**: 開発ハーネス設計書の目的が「要件定義から実装完了までを**再現性高く**進める」。基本方針8原則（成果物主義・工程分離・作成とレビューの分離・TDD・結合保証・決定論的ゲート・推測禁止・トレーサビリティ）は、すべてブレを潰すための装置。
- Effort とモデルの使い分けは `patterns/assets/claude-code-model-effort-selection-guide.png` が参考図。「モデル＝能力、Effort＝徹底度」の2ダイヤル。結果が不十分なとき、知識不足なら上位モデル、読み飛ばし・テスト不足ならEffortを上げる。
- 「上振れを伸ばす」より「下振れを切る」が本質。チーム運用では、最高の1回より**最低ラインの保証**が価値になる。
- 別の言い方: ハーネスは**分散を小さくする**装置であって、平均を上げる装置ではない（平均を上げるのはモデルの仕事）。
- 反論への備え: 「モデルが賢くなれば要らなくなるのでは？」→ 非決定性は能力とは別問題なので消えない。ただし**必要な部品は減る**。だから定期的に「この制約はまだ必要か」を見直して削るのが正しい運用（研究パターン11「能力連動の段階的簡素化」）。

## スライド5: ハーネスとは — 人に依存しない作業環境

**スライドに載せる要点**

> **ハーネスとは、コンテキスト・スキル・エージェントを揃えて、
> 「人に依存しない作業」が行える環境を用意すること**

| 揃えるもの | 中身 | 潰すブレ |
|---|---|---|
| **コンテキスト** | 組織全体のルール／チームごとのルール／ナレッジ | 人によって**前提が違う** |
| **スキル** | シニアエンジニアの知見を**手順化**したもの | 人によって**やり方が違う** |
| **エージェント** | 専門家として作業する**カスタムサブエージェント** | 人によって**見る観点が違う** |

- ベテランの頭の中にあった暗黙知を、**ファイルに出して全員に配る**
- 「あの人がやればうまくいく」→「**誰がやっても同じ手順を通る**」
- 属人性の排除は、**人を置き換える話ではない**
  - 人は判断に集中し、**手順と観点はハーネスが保証する**

**台本**
> ではハーネスとは何か。私の言葉で定義するとこうなります。**コンテキストとスキルとエージェントを揃えて、人に依存しない作業ができる環境を用意すること**です。
>
> コンテキストは、組織のルール、チームのルール、ナレッジ。これで人によって前提が違うブレが消えます。スキルは、シニアエンジニアが頭の中でやっている手順を書き出したもの。人によってやり方が違うブレが消えます。エージェントは、セキュリティを見る人、テストを見る人、という専門家。人によって見る観点が違うブレが消えます。
>
> つまり、**ベテランの頭の中にあった暗黙知をファイルに出して全員に配る**ことです。「あの人がやればうまくいく」を「誰がやっても同じ手順を通る」に変える。
>
> ひとつ補足すると、これは人を置き換える話ではありません。人は判断に集中して、手順と観点の抜けはハーネスが保証する。**役割の分担**です。

**補足（質疑用）**
- 外部の定義と一致する: Addy Osmani は "Agent = Model + Harness. If you're not the model, you're the harness." と言っている。モデル以外のすべてがハーネス、という整理。ここで挙げた3層はその具体化。
- 「すでにやっていること」でもある: CLAUDE.md を書く、権限を設定する、レビュー観点をまとめる。新しく始める話ではなく、**それらに名前がついて設計対象になる**という話。
- 暗黙知の形式知化という意味では、従来のコーディング規約やレビューチェックリストの延長線上にある。違いは、**それをAIが実際に読んで実行する**点。ドキュメントは読まれないと意味がないが、ハーネスの構成要素は必ず読まれる。
- scaffold との違い: scaffold は「モデルの振る舞いを決める層」、harness は「モデルを呼びツール呼び出しを処理し停止を判断する実行層」。2026年時点では scaffold は"いずれ不要になる仮設"、harness は"モデルの周りに残り続けるもの"というニュアンス差。

## スライド6: 3層＋「守らせる」層

**スライドに載せる要点**

| 層 | 実体 | 役割 |
|---|---|---|
| **コンテキスト** | `CLAUDE.md` / `.claude/rules/` | 常時必要な規約 |
| **スキル** | `.claude/skills/<name>/SKILL.md` | 必要なときだけ読む手順 |
| **エージェント** | `.claude/agents/<name>.md` | 独立コンテキストの専門作業 |
| ⚠️ **強制** | Hooks / permissions / テストの終了コード | **AIの判断に任せない** |
| ⚠️ **状態** | Git / 進捗・handoffファイル | セッションをまたぐ |

- 上3層は「**読ませるもの**」— 助言なので、守られない可能性がある
- 下2層は「**守らせるもの**」— スクリプトが機械的に止める
- **助言と強制を分けるのが設計の要点**
  - 例外なく守らせたいことは Hook へ。CLAUDE.md に書くだけでは足りない

**台本**
> いま挙げた3つを、実際のファイルに落とすとこうなります。コンテキストは CLAUDE.md とルールファイル。スキルは SKILL.md。エージェントは agents 配下の定義ファイルです。
>
> ただ、この3つだけだと足りません。全部「AIに読ませるもの」だからです。読ませたものは助言なので、守られないことがある。
>
> なので下2つを足します。フックや権限設定は、AIの判断に任せずスクリプトで機械的に止める。テストの終了コードで合否を決めるのも同じで、Effortやモデルに依存しません。それと状態をファイルに置いて、セッションが切れても失われないようにする。
>
> **助言と強制を分ける**、これが設計の要点です。例外なく守らせたいことは、CLAUDE.md に書くのではなくフックにする。書いてあるのに守られない、という事故はこれで防げます。

**補足（質疑用）**
- 公式の推奨順序: CLAUDE.md → 権限 → Hooks → Skills → Subagents → MCP。必要になったものから足す。最初から全部作らない。
- Hooks は「毎回必ず起こしたいこと」だけに使う。CLAUDE.md（助言的）では担保できない決定論的処理が対象。
- Skills が CLAUDE.md と別にある理由: CLAUDE.md は常時読まれるので肥大すると重要ルールが埋もれる。ときどきしか要らない専門手順は Skill に逃がしてオンデマンドで読ませる。
- 意図的負債には **Change Intent Record**（目的・理由・制約・却下案を短く残す規約）。`patterns/change-intent-record.md`。

## スライド10: チーム共有 — どう配るか

**スライドに載せる要点**
- `install-harness.sh` — **冪等**な導入スクリプト（`--dry-run` / `--verify-only` / プロファイル切替）
- **配布元から導入先を指して実行する**（インストーラを配布先にコピーしない）
  - 理由: 防ぎたい障害は「コピー漏れ」そのもの。インストーラ自身が同じ漏れの対象になってはいけない
- **managed と owned を分ける**
  - managed（hooks・agents・rules・skills）＝無条件で雛形へ揃える。アップグレード経路になる
  - owned（settings.json・allowlist）＝利用者所有。既存があれば上書きしない
- `verify-harness-install.sh` で導入診断（FAIL 0件で成功）

**台本**
> 配り方です。手作業のコピーはやめました。置き忘れや実行権限の付け忘れが起きると、安全側に倒す設計の都合でコマンドがほぼ全部拒否され、原因も分かりにくいからです。代わりに冪等なスクリプトを用意しました。何回流しても同じ状態になります。
>
> 設計の勘所を2つだけ。ひとつは、インストーラを配布元に置いたまま導入先を指して実行すること。導入先にコピーする形だと、防ぎたかったコピー漏れの対象にインストーラ自身がなってしまうので。
>
> もうひとつは、配布物を2種類に分けたことです。hooksやエージェント定義は無条件で最新に揃える。これがアップグレード経路になります。一方 settings.json はプロジェクトの持ち物なので絶対に上書きしない。この線引きがないと、更新のたびにチームのカスタマイズが吹き飛びます。

## スライド11: 規模に応じた3つのハーネス

**スライドに載せる要点**
- 図版3枚を並べる（マイクロバグ修正／軽量機能追加／開発ハーネス）
- 全部に重い工程を適用しない。**リスクと波及範囲で選ぶ**

| ハーネス | 対象 | 特徴 |
|---|---|---|
| Micro Bugfix | 再現条件が明確な局所バグ（1〜3ファイル） | 単一セッション、回帰テスト先行 |
| Lightweight Feature | 小規模機能（3〜10ファイル） | 永続状態を持たない |
| Development | 要件定義〜完了監査 | PHASE-0〜10、複数セッション再開可能 |

- 工程を減らしても、TDDと独立レビューは省略しない

**台本**
> ハーネスは1種類ではありません。規模に応じて3つ用意しています。
>
> 一番軽いのがマイクロバグ修正。再現条件がはっきりしている局所的なバグを、単一セッションで直します。次が軽量機能追加。10ファイルくらいまでの機能を、進捗ファイルなしで回します。一番重いのが開発ハーネスで、要件定義から完了監査まで11工程あります。
>
> 選ぶ基準はファイル数ではなくて、リスクと波及範囲です。小さい変更でも認証や権限に触るなら重いほうを使います。
>
> それと、軽いハーネスでも省略しないものがあります。テストを先に失敗させることと、独立したレビューです。ここを省くと、症状だけ抑えてテストを弱めて「グリーンになりました」という結果になりがちなので。

## スライド12: 自作スキル3件

**スライドに載せる要点**

| スキル | 役割 | 設計の勘所 |
|---|---|---|
| `harness-orchestration` | 11工程の制御層。`status`/`続きから`/`next`/`gate` | **成果物主義**: 会話履歴ではなくリポジトリのファイルが真実 |
| `tdd-development` | テスト設計とRED-GREEN-REFACTOR | コマンドとexit codeの証跡がないゲートは通さない |
| `diff-review` | 工程非依存の汎用レビュー | **反証ゲート**＋`disallowed-tools`で修正不能に |

- `diff-review`: 149行に凝縮（従来のレビューエージェントは719行）
- レビュー品質は**指摘の量ではなく、指摘を出さない能力**で決まる

**台本**
> 作ったスキルを3つ、設計で何を考えたかを中心に紹介します。
>
> 1つめ、ハーネスの制御スキル。「続きから」と打つと前回止まった場所を復元します。大事にしたのは、状態を会話履歴から推測しないこと。真実はリポジトリのファイルだけです。会話は消えてもファイルは残るので、セッションをまたいでも再開できます。
>
> 2つめ、TDD用のスキル。「テストが通りました」という自然言語の宣言は証拠として認めません。コマンドと終了コードの記録がないとゲートを通れません。
>
> 3つめ、レビュースキル。レビューの質は指摘の量ではなく、余計な指摘を出さない能力で決まると考えました。報告前に「実際に壊れる入力を具体的に書けるか」を必ず通し、書けないものは捨てます。さらにこのスキルからは編集ツール自体を取り上げました。「修正するな」と本文に書いても回避されえますが、ツールを渡さなければ回避できません。禁止は文章ではなく仕組みで強制する、という考え方です。

## スライド13: 24エージェント — 作る人と見る人を分ける

**スライドに載せる要点**
- 図版: 開発ハーネス全体図
- 24エージェントを4系統に分類: **Planner / Generator / Evaluator / Orchestrator**
- **Generator と Evaluator は必ず別実行** — 自己評価バイアスを構造で排除
- 例:
  - `security-reviewer` — code-reviewer の PASS を自分のPASSの根拠にしない
  - `ui-verifier` — 検証できなければ "unverified"（PASSではない）＝完了ブロック
  - `completion-auditor` — 要件→受入基準→タスク→テスト→実装のリンク切れを監査

**台本**
> エージェントは24件ありますが、4つの系統に分かれています。計画する人、作る人、評価する人、全体を仕切る人です。
>
> 一番の方針は、作る人と評価する人を必ず別々に動かすこと。同じセッションで自分の書いたコードをレビューさせると、どうしても甘くなります。
>
> 例を2つ。UI検証の担当は、確認できなかったとき「未検証」を返します。これは合格ではないので完了がブロックされます。「確認できなかった」を「問題なし」に変えないための設計です。
>
> もうひとつが完了監査で、要件からテスト、実装までのつながりが切れていないかを機械的に見ます。「実装したつもりで要件が1つ落ちている」を拾えます。

## スライド14: まとめ

**スライドに載せる要点**
- AI駆動開発では、**人は書く側から検証する側へ**回る
- 律速は「書く速度」から「**検証する速度**」へ
- 壁の根っこは「**同じことを頼んでも同じ結果が返らない**」— モデル・人・モデル選択・Effortでブレる
- だから**出力のブレを、結果のブレにしない仕組み**が要る
- それを実現するのが **ハーネス** = コンテキスト・スキル・エージェントを揃えた**人に依存しない作業環境**
- 個人の工夫を**配布物**にすればチームの資産になる
- まず Step 1 に全員、慣れた人から Step 2

**台本**
> まとめます。
>
> AI駆動開発では、人は書く側から検証する側へ回ります。そこでぶつかる壁の根っこは、同じことを頼んでも同じ結果が返らないことでした。モデルも、使う人も、モデル選択も、Effortもブレる。補助ツールならその場で弾けますが、中核に置くと弾けません。だから、出力のブレを結果のブレにしない仕組みが要る。それがハーネスでした。
>
> 成果を分けるのはモデルそのものより、その周りを固めるハーネスのほうです。制御はできるだけコードと権限に追い出して、AIには狭い自由度を渡す。
>
> そして、個人の工夫のままにせず配布物にすれば、チーム全体の資産になります。うちのハーネスは導入スクリプト1本で入るので、試したい方は声をかけてください。
>
> まずは全員が Step 1 に慣れること。そこから並列化を試していきましょう。以上です。

## 質疑応答の備え

| 想定質問 | 答えの骨子 |
|---|---|
| 「コストは？」 | 既定モデル方針と支出キャップを決める。日常は標準モデル、難しい設計判断だけ上位モデル。コンテキスト肥大はコストにも品質にも悪影響なので `/clear` とサブエージェントで抑える。参考図: `patterns/assets/claude-code-model-effort-selection-guide.png` |
| 「効果測定は？」 | 週間アクティブ開発者数、開発者あたりセッション数、レビューでの重大指摘率、rollback率、リードタイムの変化。導入前にベースラインを取っておくのが肝。展開中は隔週、定常後は月次でレビュー |
| 「AIレビューで人のレビューは要らなくなる？」 | ならない。外部影響のある操作（protected branchへのmerge、本番データ変更、認証・認可・秘密情報、破壊的API変更、依存追加）は人間承認を残す。判断は安全側に倒す |
| 「重すぎない？」 | だから3段階ある。小さいバグにフル工程は適用しない。必要になるまで複雑性を足さないのが原則 |
| 「導入の手間は？」 | スクリプト1本＋診断1本。dry-runで事前確認できる |
| 「よくある失敗は？」 | 無関係タスクを1セッションに混ぜてコンテキストを汚す／同じ訂正を繰り返して失敗案が蓄積する（2回失敗したら`/clear`して指示を書き直す）／CLAUDE.mdが肥大して重要ルールが埋もれる |
| 「本当に速くなるの？」 | 短期では**遅くなりうる**（Jカーブ）。DORAはスループット向上の一方で安定性低下を報告している。**数字は約束しない**——「検証を機械に寄せた分だけ効く」と言うほうが誠実で、実際の効果はうちで計測する。体感と実測がズレる例としてMETRのRCTもあるが、同社が後に限界を公表しているので断定には使わない |
| 「AIが書いたコードの保守は？」 | ここが認知的負債・意図的負債の話。動くコードより「なぜそう作ったか」が消えるほうが痛い。Change Intent Recordで目的・理由・制約・却下案を短く残し、会話履歴を設計文書の代用にしない |
| 「仕様駆動とどう違う？」 | 対立しない。仕様駆動は入口（何を作るか）を固める話で、ハーネスは全工程（どう検証し、どう再開し、どう権限を絞るか）の話。うちのPHASE-1〜2が仕様駆動に相当する |
