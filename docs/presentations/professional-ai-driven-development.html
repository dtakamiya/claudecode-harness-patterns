制御の優先順位：X → Y → F

コンテキストの7要素

プロンプト都度手書き
ルール自動読込の常設指示
コードベース量最大・暗黙の手本
ドキュメント意図・背景
スキル該当時のみ読込の手順
外部情報接続して届く事実

  • 入り方は3通り：人が入力／ハーネスが自動読込／ツール結果として届く

品質の3原則（全体像）

鮮度現在の事実と一致
必要十分性過不足なし
一貫性矛盾なし
  • いずれかが崩れた状態が「コンテキストの劣化」
  • 正確→鮮度／短く具体的→必要十分性／整合→一貫性

原則1：鮮度

  • AIは与えられた情報の真偽を検証しない
  • 古い情報は「誤った正解」になる
  • 例：旧APIパス、旧importの残骸が手本にされる
  • 作成時点で更新が止まった文書＝タイムカプセル仕様書
  • 名前をつけてレビューの点検観点にする

原則2：必要十分性

  • 不足：暗黙ルールが未明文化だと推測任せになる
  • 過多：前タスクの履歴の持ち越しが雑音になる
  • 不要情報は中立でなく、必要情報を埋もれさせる（Context Rot）
  • Anthropicの定義：最小で高密度なトークン集合
  • 自問：「今、必要十分な情報を渡せているか」

原則3：一貫性

ルールORM必須と宣言
既存コード生SQLが大半
  • 矛盾は「二枚舌ルール」。AIは確率的に片方を選び、出力が揺れる
  • 原因：同一の事実が複数箇所にある
  • 解決：SSoT（事実の置き場所を1箇所に限る）

3原則を守る対策：3つの時点

実行前生成前に整える
6要素の整備
→
実行時生成中に制御
プロンプト・分割
→
実行後生成後に片付ける
リファクタリング
  • 基準は「次の1回の生成」
  • 目視では守れない。仕組みと習慣で守る

実行前：ルールとコードベース

  • ルール：簡潔に（ルートは索引）
  • 機械的に従える具体性で書く。曖昧語は挙動を変えない
  • 単一情報源を1箇所に。乖離は即どちらかに合わせる
  • コードベース：不要コードを削除、1ファイル1責務
  • 各フォルダに責務1行のREADME（索引）、重複実装は共通化

実行前：ドキュメントとスキル

  • ドキュメント：実装変更のPRで仕様書も同時更新
  • 維持できない文書はXから外し、コードを真実とする
  • 「なぜ」を残す：局所はコードコメント、横断はADR
  • ADRは追記型。覆っても消さず「置き換え済み」の印
  • スキル：繰り返す手順を切り出す。手順変更時は更新

実行前：外部情報と対話履歴

  • 外部情報：未接続の情報はAIに存在しない
  • ログ基盤・DB・タスク管理・GitHub・Web調査など
  • CLIとMCPを使い分ける。MCPのツール定義は常時Xを占有
  • 必要なものから接続し、不要なものは外す
  • 対話履歴：捨てて整える。意味の区切りで新セッション
  • コンパクトは応急処置。本命は新セッション

曖昧語を避ける

  • 毎回長くなるなら環境整備不足のサイン

実行時：サブエージェント分割（3パターン）

Fan-out独立した仕事を並列実行
Pipeline前段の出力が次段の入力
例：DB→API→フロント
Specialist領域別に振り分け
例：セキュリティ・性能

  • 分割は無料でない。各自が文脈を掴み直す

  • 劣化は自己増幅し、1周ごとに加速する
  • 負債は「いつか」でなく次の1タスクに効く
  • 美化活動でなく、実装完了確率を守るインフラ投資

まとめ

第4章

アウトプット制御のためのテスト駆動開発

Y の制御：合格基準を先に定義する

第4章の導入：Yの制御（テスト駆動開発）

  • Xを整えても、Fは確率マシンなので出力は揺れる
  • 本章は揺れる出力を受け止める側、Yの制御
  • Yの制御＝合格基準を先にテストで定義し、通った出力だけ受け入れる
  • 前半：速度と品質のトレードオフとテストの位置づけ
  • 後半：テストの作り方、テスト自体の品質、守れる範囲

4.1 速度と品質のトレードオフ

判定の担い手速度品質
人間が判定（レビュー・目視）×：確認待ちで頭打ち○：人間の目で守る
判定を省く（バイブコーディング）○：確認なしで進む×：検証なき信頼で崩壊
機械が判定（テスト）○：AIが合格まで自走○：ぶれない基準で検証
  • 根の問いは「AIの出力を誰が正しいと判定するのか」
  • 出力は確率的に揺れるので、判定は省略できない
  • 機械判定の行だけが速度と品質を両立する

人間が判定すると頭打ちになる

人間が指示
→
AIが実装
→
人間が確認修正依頼
→
AIが再実装
  • Human in the Loop：確認と修正依頼の往復が続く
  • AIは自分で正誤を判定できず、人間がテスター兼デバッガーに
  • コンテキストスイッチで時間が消え、確認まで非同期にならない
  • 時間の大半はデバッグ待ち。書く速度だけ上げても全体は約1.2倍止まり
  • ボトルネックは「書く速度」でなく「正しいと確かめる速度」

判定を省くと品質が崩れる

  • 省けば速いが、それはバイブコーディング（なんとなく動けばOK）
  • 事例：「コード凍結」を明示指示したのに、AIが本番DBを削除
  • 指示の明確さと出力の正しさは別問題
  • 誤りを本番で初めて発見することになる
  • 欠陥の蓄積で保守不能に（第1章「3ヶ月の崖」）

4.2 テストという「正解の定義」

  • 機械は善し悪しを勝手に見抜けない。正解を書き下す道具がテスト
  • テスト＝「こう操作したらこうなるのが正解」をコード化したもの
  • 結果はpass/failに機械的に決まり、解釈の余地がない
  • 自然言語の「購入できる」は範囲が曖昧（カート？決済？配送？）
  • 制約の正体は、正解を事前に定義していなかったこと

機械の判定の3つの性質

速い数秒で結果が返る
何度でも深夜・休日でも実行できる
ぶれない100回目も1回目と同じ基準
  • 人間の判定は「遅い・回数に限りがある・ムラがある」
  • 機械の判定はその裏返し
  • 速度の頭打ちも品質のムラも同じ一手（機械への交代）で崩れる
  • 前提：テスト自体が正しく書かれていること

4.3 テストがAIを自走させる

人間指示（テストを先に）
→
AI実装→リント→テスト
→
AI失敗を読んで修正・再実行
→
全テスト合格完了報告
→
人間検収
  • テストなし＝準委任：「頑張りました」で終われる
  • テストあり＝請負：全テスト通過が完成条件
  • リントの「エラーゼロまで直して」が最小の自走例
  • 人間が関わるのは最初の指示と最後の検収だけ

AIが自律する3つの条件

明確なゴール定義テストが正しさを定義
自動実行環境AIがコマンド1つでテスト実行できる
エラー情報の可読性失敗が文字で読める
  • ツールにテスト実行の権限を与える
  • 画面を目で見ないと分からない失敗はAIに読めない
  • 3条件が揃えば、合格までAI単独で回る（環境の整備は第7章）

人間の仕事は「定義」と「検収」

人間要件整理・テストで合格基準を定義
AI実装・テスト・修正を自律反復
人間全テスト通過後に検収
  • 実装者から設計者・検収者へ役割が移る
  • 試行錯誤中は張り付き不要。別タスクに集中できる
  • デバッグまでAIが回せ、守備範囲が「書く」から全体へ広がる
  • 5〜10倍短縮は射程に入るが、正しく運用した場合の理論値

4.4 テストが最後の検証点になる

  • 人間の目は全コードを追えない（レビューは処理能力を超えて溢れる）
  • CIのテストが品質保証の本体。失敗すれば自動で止まる
  • リグレッション（過去機能の破壊）を、壊れた瞬間にfailで検知
  • AI生成コードはエッジケースで壊れやすく、境界値・異常系のテストが有効
  • AIレビューは同じ基準で判断するので、止める装置はテストだけ

テストの2つの価値

速度AIを自走させる燃料
Greenまで自律反復
品質最後の検証点（ブレーキ）
CIの品質ゲートで自動ブロック
  • ブレーキのないスポーツカーにしない
  • AIが進化しても誤りの確率はゼロにならない
  • 人間がループから外れるほど、検証点の重みは増す

4.5 従来のTDDと本書の違い

観点従来のTDD本書のTDD
サイクルの主体人間AI
テストの目的設計のやりすぎ・やらなさすぎを防ぐAI出力への自動フィードバック
歩幅最小（1テストずつ）選べる（一括でGreenも可）
  • 小さな歩幅は、人間の実装コストの高さが強いた規律
  • AIは書き直しが数分で済むので、刻む理由は薄まる
  • 守るのは「小さく分割して考える」「小さく書いて確かめる」

4.6 何を・どう・いつテストするか：配分3ステップ

1. 機械で判定できるかNo：手動確認・人間レビュー
→
2. 主要フロー／重要な異常系Yes：E2Eへ
→
3. 残りの細部単体・結合へ
  • 高くつくのは書く時間でなく、変更のたびの実行時間
  • 厚みは障害時の影響で決める（決済・データ削除は最も厚く）
  • 見た目や本番でしか出ない挙動は、テストでなく人間が担う

E2E・単体・結合の役割とピラミッドの反転

従来底辺：単体（大量）
頂点：E2E（少数）
AI時代E2Eを厚く
単体は精鋭化して絞る
  • E2E＝手動確認をそのままコード化。ユーザー視点で書け、失敗もAIに伝わりやすい
  • セルフヒーリング：壊れたE2EをAIがログを読んで直し、運用コストが下がる
  • 単体・結合は速く安定し、境界値や極端な異常系の網羅に向く
  • いつ書くかは目的で選ぶ。ただし本番投入時にはテストがある状態にする

4.7 AIが生む「悪いテスト」と対策

意味のない通るテスト何を返しても通る検証
ダミー返却外部をダミーに置換して未検証
意図的スキップ条件を仕掛けて実行させない
  • 原因は不注意でなく最適化の方向：Goodhartの法則（目標になった指標は良い指標でなくなる）
  • 実装からテストを作ると、誤りごと正しいと写し取る循環になる
  • 実体験：テストが通っていたのは「AIが作った偽の世界」だけだった

WHATは人間・HOWはAI

人間シナリオ列挙（異常系・境界値まで）
→
AIテストコードに変換
→
人間アサーションをレビュー
  • AIのテストは明示しないと正常系に偏る
  • 正解の定義を実装から独立させ、人間が持つ
  • まず実装なしで実行しRedを確認する
  • ミューテーションテスト：実装を壊してもテストが通るなら、何も検証していない
  • テストコードにもAIレビュー（スキップ・細工の有無）を適用する

4.8 テストで守れる範囲と守れない範囲

内側：テストが守る機能の正しさ（pass/failに書ける振る舞い）
外側：守れないUIの心地よさ／性能の体感／セキュリティの証明／ビジネスの妥当性
  • 外側は増やしても解決しない。別の制御へ明示的に手渡す
  • 定性評価 → 第6章（AI相互レビュー＋人間レビュー）
  • 本番でしか分からない問題 → 第8章（段階的リリース＋監視）

4.9 テストがAIのコンテキストになる循環

Yテストが正誤を判定
→
蓄積通ったコードだけ残る
→
Xテストが次の手本になる
→
生成パターンに沿って出力
  • AIは既存テストを読み、書き方や例外処理の流儀を学ぶ
  • 良いテストは高品質な生成を、低品質なテストは低品質の再生産を招く
  • テストは最も曖昧さの少ないコンテキスト
  • Yの品質保証とXの品質向上を一度に達成できる（一石二鳥）

4.10 第4章まとめ

  • 人間が判定すると遅く、省くと崩れる。正解を機械判定できる形で先に書く
  • 機械判定でAIは自走し（速度）、人間レビューに頼らない品質保証も成り立つ
  • TDDの駆動軸だけを継承：正解の定義は人間が実装から独立して行う
  • AIはテストを通すことに最適化する。WHAT/HOWの分業とテストレビューで守る
  • テストは燃料であり最後のブレーキ。守れる範囲は機能の正しさまで
