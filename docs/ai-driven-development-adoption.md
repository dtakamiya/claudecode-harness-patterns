# Claude Code 前提の AI 駆動開発 導入手順書（小規模チーム版）

> 想定読者: 導入責任者（DRI）と開発エンジニア。対象規模: 単一チーム 〜10名。
> この手順書は Anthropic 公式ドキュメントと公開されているロールアウト事例のみを根拠に作成した**汎用テンプレート**です。特定リポジトリの独自資産には依存しません。導入対象リポジトリの `docs/` またはチーム Wiki にコピーし、チームの実態に合わせて調整して使ってください。

---

## 1. 狙いと前提

### 何を変えるのか

Claude Code を「コード生成ツール」ではなく **思考パートナー兼実装エージェント** として開発フローに組み込みます。Claude Code はチャットボットと違い、ファイルを読み、コマンドを実行し、変更を加え、問題を自律的に解いていきます。エンジニアは「何を作るか」を記述し、Claude が探索・計画・実装・検証を回します。

Anthropic 社内チームの活用例（公式ブログより）:

- **新規メンバーのオンボーディング**: コードベースについて「シニアエンジニアに聞くような質問」を Claude に直接投げてランプアップを短縮。
- **インシデント診断**: スタックトレースとドキュメントを与えて制御フローを追跡し、診断を高速化。
- **テスト・レビューの自動化**: GitHub Actions で PR レビューを自動化し、フォーマット指摘やテストのリファクタを任せる。
- **思考パートナー**: 最も成功しているチームは、コード生成ツールとしてより「可能性を探索し素早くプロトタイプを作る相棒」として使っている。

### 前提と非目標

- **前提**: `gh` CLI がインストール済み／git 運用がある／main への直接コミットを避ける運用ができる。
- **非目標**: 本番デプロイ自動化、CI/CD 基盤の新規構築、特定技術スタックへの最適化。まずは開発フローへの組み込みに集中します。
- **原則: ビッグバン導入をしない。** 全員に一斉必須化するとツールを理解しない懐疑派を生み、定着を阻害します。段階展開＋チャンピオンで進めます。

## 2. プロセスはどう変わるのか（従来型開発 → AI 駆動開発）

AI 駆動開発は、既存のプロセスに「速いコード生成」を足すものではありません。**エンジニアの役割そのものが「実装者」から「意図の記述者・検証者・オーケストレーター」へ移り**、工程の重心が変わります。

### 工程ごとの変化

| 工程 | 従来型（AI なし） | AI 駆動開発 |
|---|---|---|
| コードベース理解 | 有識者に聞く／ドキュメントを読み漁る。ランプアップに数日〜数週間 | Claude に「シニアに聞くような質問」を直接投げ、その場で把握 |
| 要件・仕様 | 人が仕様書を書く | Claude にインタビューさせ、抜けを洗い出して `SPEC.md` に固める |
| 設計 | 人が設計し、レビューで検証 | plan mode で探索→計画を先に固め、間違った問題を解く事故を防ぐ |
| 実装 | 人が手で書く（律速工程） | Claude が実装。人は方針提示と軌道修正。**ここが最大の短縮点** |
| テスト | 実装後にまとめて書く／後回しになりがち | 「検証手段（テスト/ビルド/スクショ）」を先に与え、Claude が自分で検証ループを回す |
| コードレビュー | レビュー待ちがボトルネック | 新鮮なコンテキストの subagent で一次レビュー。人は残った価値判断に集中 |
| デバッグ | 人がログ・スタックトレースを追う | スタックトレースを貼れば原因追跡を高速化 |
| 反復 | 変更コストが高く、試行錯誤しにくい | チェックポイント/`rewind` で「まず試して、だめなら戻す」が安価に |

### 何が「律速」だったかが変わる

- **従来**: ボトルネックは「コードを書く速度」。人手の実装時間が全体を律速していた。
- **AI 駆動**: 実装は速くなり、ボトルネックは **「意図を正確に伝えること」「出力を検証・レビューすること」「コンテキスト管理」** へ移る。だから CLAUDE.md・検証手段・レビュー体制への投資が効く。

### 変わること／変わらないこと

- **変わること**: 実装の担い手、工程の重心（書く→検証する）、試行錯誤のコスト、オンボーディングの速さ、1人あたりの並列作業量。
- **変わらないこと（むしろ重要度が増す）**: 何を作るかの意思決定、外部影響のある操作への**人間の承認**、テストと検証の規律、設計意図の記録。**AI レビューが人間の承認を代替することはありません**（§5）。

> 移行の指針: この変化は一度に起きません。§4 の段階展開ロードマップと §3 の成熟度モデルに沿って、まず「人が全変更を読む」Step 1 から始め、検証ループとレビュー体制が整った領域から段階的に自動化を広げます。

## 3. 成熟度モデル（現在地と目標の共有）

Claude Code の生みの親 Boris Cherny による「Steps of AI Adoption」を、チームの共通言語として使います。トークン消費を増やすだけでは次段階に進めず、各段階の**ボトルネック解消**と**ガードレール構築**が鍵です。

| Step | 呼称 | エンジニアの役割 | アンロック | ボトルネック |
|---|---|---|---|---|
| 0 | Gated | AI アクセスなし | なし | レガシー承認プロセス |
| 1 | Assisted（〜1体） | あなた＋エージェントのペアプロ、1セッション監視 | 午後かかる作業が会議の合間に完了 | あなたの注意力・全変更を読む必要という信頼不足 |
| 2 | Parallel（〜10体） | オーケストレーター、複数 worktree を管理 | 数週間のバックログを1人の午後で処理 | 多数の出力レビューとセッション間の操舵 |
| 3 | Supervised autonomy（〜100体） | マネージャー・オブ・マネージャー | 継続的なバックグラウンド保守 | ループへの信頼とチームの意思決定スループット |
| 4 | AI-native（1,000体＋） | 意図で動く VP | 四半期規模の作業がキックオフ＋監視で完了 | 自動化対象の特定と作業種別ごとのガードレール |

**小規模チームの目標**: まず全員を **Step 1（Assisted）** に定着させ、慣れたメンバーから **Step 2（Parallel）** を試す、が現実的です。判断基準はシンプルに「そのタスクをエンジニアがやったはずなら自動化、そうでないなら人間ゲートを残す」。

## 4. 段階展開ロードマップ（小規模チーム版）

各フェーズを **入口条件 / やること / 出口条件（Go/No-Go）** で管理します。

### Phase A: 準備（目安 数日）

- **入口条件**: 経営/リードが「試す」ことに合意している。
- **やること**:
  - **DRI（単一責任者）を1名指名**する（§5）。
  - **パイロット参加者を2〜3名**選ぶ（経験レベルを混ぜる。おもちゃではなく**実プロジェクト**を対象に）。
  - **成功指標（KPI）を先に定義**し、ベースライン（現在のリードタイム/レビュー時間など）を控える（§8）。
  - Claude Code の課金と、既定モデル・支出キャップ方針を決める（§9）。
- **出口条件**: DRI 決定・対象リポジトリ確定・KPI とベースライン記録済み。

### Phase B: パイロット（目安 1〜2週間）

- **入口条件**: Phase A 完了。
- **やること**:
  - 対象リポジトリに **CLAUDE.md と共有設定を整備**する（§6）。
  - パイロット2〜3名が **日常タスクを一巡**させる（探索→計画→実装→コミットのワークフローで）。
  - **1時間のハンズオン**（§7）を実施し録画する。
  - 詰まりどころ・CLAUDE.md の過不足・権限の摩擦を DRI が収集し、設定を調整する。
- **出口条件（Go/No-Go）**: 参加者が週3回以上使用／`/status` で共有設定が正しく読み込まれる／重大な運用ブロッカーが解消済み／参加者が「他メンバーに勧められる」と回答。**満たさなければ Phase C に進まず Phase B を延長**。

### Phase C: チーム全体展開（目安 1〜2週間）

- **入口条件**: Phase B の Go 判定。
- **やること**:
  - 残りメンバーへ展開。パイロット参加者が**チャンピオン**として伴走。
  - 録画ハンズオンで非同期オンボーディング。新規参加者は「導入済みリポジトリ＋この手順書」で立ち上がれる状態にする（セルフサービス化）。
  - 日常ワークフロー規約（§6）をチーム標準として周知。
- **出口条件**: 有効利用率が定常化し、KPI レビュー（§8）が回っている。

## 5. 役割とガバナンス

### DRI（Directly Responsible Individual）

技術設定の分散を防ぐため、以下を1名に集約します:

- `CLAUDE.md` 規約とテンプレート（簡潔に保つ・git 管理・定期プルーニング）。
- `.claude/settings.json`（permissions・hooks・model 方針）の管理。
- `.claude/skills/`・`.claude/agents/`・MCP サーバーの追加/変更審査。

### 設定の階層と共有（公式の優先順位）

Claude Code の設定は次の優先順位で解決されます（高→低）。チーム共有はプロジェクトスコープに置き、個人設定と分離します。

| スコープ | ファイル | 用途 |
|---|---|---|
| Managed（最優先・上書き不可） | MDM/サーバー配布 | 組織ポリシー（大規模時） |
| Local（個人・gitignore） | `.claude/settings.local.json` | 個人の上書き |
| **Project（チーム共有・git 管理）** | **`.claude/settings.json`** | **チーム標準。ここを整える** |
| User（個人・全プロジェクト） | `~/.claude/settings.json` | 各自の既定 |

- チーム共有の `CLAUDE.md` と `.claude/settings.json` は **git にコミット**して全員で改善する。
- 個人の実験的設定は `.claude/settings.local.json`（gitignore）へ。
- 読み込み状態は `/status` で確認できる。

### 人間ゲート（承認）の考え方

- **AI レビューは人間の承認を代替しない。** コードレビューやセキュリティレビューを Claude に任せても、外部に影響する操作（protected branch への merge、本番/共有データへの変更、認証・認可・秘密情報、破壊的 API、依存追加）は**人間が承認**する。
- **fail-closed（安全側に倒す）**: 検証が未完了・曖昧なら「許可」ではなく「停止」。
- **判断基準**: 「そのタスクをエンジニアがやったはずか？」Yes なら自動化を進め、No なら人間ゲートを残す。
- 承認の重さは、ファイル数ではなく**利用者影響・データ影響・可逆性・権限・波及範囲**で決める。

## 6. 環境セットアップと日常ワークフロー規約

### 5.1 環境セットアップ（公式ベストプラクティス）

拡張レイヤーは **CLAUDE.md → 権限 → Hooks → Skills → Subagents → MCP** の順に、必要になったものから足します。

1. **CLAUDE.md を用意**する。`/init` で雛形を生成し、その後手で洗練する。
   - 含める: 推測できない Bash コマンド、既定と違うコード規約、テスト実行方法、ブランチ/PR 規約、環境の癖、非自明な落とし穴。
   - 含めない: コードを読めば分かること、標準的な言語慣習、頻繁に変わる情報、長い説明。
   - **簡潔に**。各行に「これを消したら Claude が間違えるか？」を問い、No なら削る。肥大化すると重要ルールが埋もれる。
2. **権限を設定**する。`.claude/settings.json` の `permissions.allow` に安全な定型コマンド（`npm run lint`、`git commit` 等）を、`deny` に危険なもの（`curl *`、`Read(./.env)`、`secrets/**` 等）を列挙。摩擦が多ければ **auto mode**（分類器が危険な操作だけブロック）や **sandbox**（OS レベル隔離）を検討。
3. **CLI ツールを使わせる**。`gh`・`aws`・`gcloud` 等をインストールしておくと、Claude が context 効率よく外部サービスを操作できる。
4. **Hooks は「毎回必ず起こしたいこと」だけ**。lint やフォーマットの自動実行など、CLAUDE.md（助言的）では担保できない決定論的処理に使う。
5. **Skills は「ときどき必要な専門知識・手順」**。`.claude/skills/<name>/SKILL.md` に置き、オンデマンドで読ませて CLAUDE.md の肥大化を避ける。
6. **Subagents は調査・専門レビュー用**。`.claude/agents/` に定義し、独自コンテキストで多数のファイルを読ませてメイン会話を汚さない。
7. **MCP は外部ツール連携**（Issue トラッカー、DB、Figma、監視データ）。必要になってから `claude mcp add`。

### 5.2 Claude Code の基本作法（公式ベストプラクティス）

- **探索 → 計画 → 実装 → コミット** を分ける。plan mode で先に探索・計画し、間違った問題を解く事故を防ぐ。1文で差分を説明できる小修正は計画を省略してよい。
- **検証手段を必ず与える（最重要）**。テスト・ビルド・スクショなど「pass/fail が返るチェック」を渡すと Claude が自分で検証ループを閉じる。成功を主張させるのではなく**証拠（テスト出力・実行コマンド・スクショ）を提示させる**。
- **具体的に指示する**。対象ファイル・シナリオ・参照すべき既存パターンを明示（`@file` 参照が有効）。大きめの機能は `AskUserQuestion` で Claude にインタビューさせ、`SPEC.md` を先に固めてから新セッションで実装する。
- **コンテキストを積極管理**。無関係タスク間で `/clear`。同じ誤りを2回超えて訂正したら `/clear` して初期プロンプトを書き直す。長い調査は subagent に逃がす。
- **敵対的レビューを1ステップ入れる**。完了扱いにする前に、新鮮なコンテキストで diff をレビュー（`/code-review` 等）。「正しさ・要件に影響する gap のみ」を指摘させ、過剰対応を避ける。
- **並列化**（慣れてきたら）: worktree で複数セッション、Writer/Reviewer パターン、`claude -p` の非対話モードで CI やバッチに組み込む。

## 7. 教育・オンボーディング

- **1時間ハンズオンを各コホートに実施**し、録画して非同期共有する。
- 3つのライブ実演で構成する:
  1. **デバッグワークフロー**（スタックトレース/エラーを貼って原因特定→修正→検証）
  2. **コードレビュー**（`/code-review` と敵対的レビュー）
  3. **CLAUDE.md ウォークスルー**（何を書き、何を書かないか）
- チャンピオン（パイロット参加者）がペア作業で伴走する。新規参加者は「導入済みリポジトリ＋この手順書」だけで立ち上がれることを目標にする。

## 8. 成功指標（KPI）とレビューサイクル

- **採用**: 週間アクティブ開発者数（WAU）。
- **利用**: 開発者あたりのセッション数。
- **品質**: ツール呼び出しのエラー率、レビューでの重大指摘率、rollback 率。
- **満足度**: 月次アンケート（5問以下）。
- **効果**: リードタイム/レビュー時間の変化（Phase A のベースラインと比較）。

テレメトリは `.claude/settings.json` の `env` で OpenTelemetry を有効化して収集できます（例: `CLAUDE_CODE_ENABLE_TELEMETRY=1`）。

**レビューサイクル**: 展開中は隔週、定常後は月次で KPI を確認。**3〜6か月ごとに設定を見直し、モデル進化で不要になった古い制約ルールを削除**する。

## 9. コスト・モデル運用

- **既定モデル方針を決める**。日常作業は標準モデル、深い設計判断・複雑な推論は上位モデルへ。`.claude/settings.json` の `availableModels` / `enforceAvailableModels` でモデルを制限できる。
- **支出キャップ**を設定し、開発者あたりコスト・WAU を監視する。
- コンテキスト肥大はコストにも品質にも悪影響。`/clear`・subagent・スコープを絞った調査でトークンを抑える。

## 10. リスクと失敗パターン

公式の「よくある失敗」と回避策:

| 失敗パターン | 症状 | 回避策 |
|---|---|---|
| kitchen sink セッション | 無関係タスクを混ぜてコンテキストが汚れる | タスク間で `/clear` |
| 訂正の繰り返し | 直しても直らず失敗案が蓄積 | 2回失敗したら `/clear` して初期プロンプトを書き直す |
| 過剰な CLAUDE.md | 長すぎて重要ルールが無視される | 容赦なくプルーニング。守れているルールは削るか Hook 化 |
| trust-then-verify ギャップ | それらしいがエッジケース未対応の実装 | 常に検証（テスト/スクリプト/スクショ）。検証できないなら出さない |
| 無制限 exploration | スコープなしの「調査」で数百ファイルを読む | 調査を狭くスコープする／subagent に逃がす |
| **ビッグバン展開** | 一斉必須化で懐疑派を生む | 段階展開＋チャンピオン（§4） |
